# T3 — RS485 bus transport (tested on its own)

This file tests **the bus**, not the modules. Every test is run **once per
module** — once with the nong board as the device under test, once with the
lift board — and the module type is a *control* variable inside each run, not
something being compared.

Why separate from T4 (WiFi) and T5 (USB): RS485 is the only transport that is
**shared, half-duplex and addressed**. Its failure modes — collisions, missing
termination, DE turnaround, frame length — do not exist on the other two, and
its independent variables (cable length, node count, termination) have no
meaning there. Testing them "all together" would mean no variable is isolated.

Source of truth: `code/firmware/src/core/RS485Bus.cpp`,
`code/firmware/COMMANDS.md` §4.

---

## What the wire does

```
wiring   RO→GPIO16 (rx)   DI→GPIO17 (tx)   DE+/RE→GPIO4   A/B to the bus   common GND
line     115200 baud, 8N1, ASCII lines terminated with \n
request  #<id> <command>      addressed        e.g.  #3 GOTO 2
request  #* <command>         broadcast: everyone executes, nobody replies
reply    @<id> <reply text>                    e.g.  @3 OK goto 2
discovery #* PING             every module replies, staggered by id × 20 ms
```

Firmware limits worth testing against:

| Limit | Value | Where |
|---|---|---|
| Receive buffer | line dropped if it exceeds **250 chars** | `RS485Bus::loop()` |
| DE turnaround | 20 µs before + `Serial2.flush()` + 20 µs after | `RS485Bus::send()` |
| Broadcast replies | only `PING` replies, staggered `id × 20 ms` | `handleLine()` |
| Send mutex | web task and main loop share one mutex | `sendMtx_` |
| File chunk | `FDATA` ≤120 bytes, `FREAD` len capped at 120 | `CommandRouter` |

## Variables

### Independent variables

| # | Independent Variable | How to set it | Range used |
|---|---|---|---|
| 1 | **Bus cable length** | swap A/B twisted pair | 0.5 m, 5 m, 20 m, 50 m |
| 2 | **Termination** | 120 Ω across A/B at each end | none, one end, both ends |
| 3 | **Node count on the bus** | power up 1…N modules | 1, 2, 4, 8 |
| 4 | **Addressing mode** | the frame you send | addressed `#<id>`, broadcast `#*` |
| 5 | **Command rate** | commands per second from the host | 1, 10, 50, 100 /s |
| 6 | **Frame length** | length of the command line | 10, 100, 240, 260 chars |
| 7 | **Module id** | `SET ID <1-247>` | 1, 3, 100, 247, and 0/248 (invalid) |
| 8 | **Concurrency** | who is sending | host only; host + a `link 1` nong leader forwarding poses |
| 9 | **Payload chunk size** | `FDATA` base64 chunk | 40, 80, 120, 160 bytes |
| 10 | **Bus idle noise** | motor/servo running or not during the traffic | idle, module moving |

### Dependent variables

| DV | Unit | How it is read |
|---|---|---|
| Reply success rate | % | `tools/bench.py rs485` — replied ÷ sent |
| Round-trip latency | ms | same tool: min / mean / p95 / max |
| Corrupted replies | count | replies that don't match `@<id> …` |
| Lost frames | count | sent with no reply inside a 2 s timeout |
| Discovery completeness | modules found ÷ modules powered | `#* PING`, count distinct `@<id>` |
| Collision evidence | count | two replies interleaved on one line |
| File transfer throughput | bytes/s | `FBEGIN`/`FDATA`×N/`FEND` of a known file |
| File integrity | pass/fail | `FREAD` the file back, compare byte-for-byte |
| Reply string | text | verbatim |

### Control variables

| CV | Fixed at |
|---|---|
| Baud | 115200 8N1 (`RS485_BAUD`) — never changed mid-series |
| Transceiver | the same MAX485-type board on every node |
| Host adapter | one USB-RS485 dongle, one COM port, one PC |
| Ground | common GND wired between all nodes and the dongle |
| Module type under test | one type per series (run the whole file for nong, then again for lift) |
| Module state | idle, `HOME`d, nothing moving (except IV #10) |
| WiFi | `SET WIFI OFF` on every node — a WiFi task must not steal CPU from the bus timing |
| Command | `PING` for all latency rows (shortest reply, no side effects) |
| Sample size | 50 commands per run, 3 runs per IV value |
| Firmware version | one build on every node |

## Tests

### RS485-01 — cable length

CV: 2 nodes, both ends terminated, 10 cmd/s, addressed `PING`.

| ID | IV setting | Command / action | Measure (DV) | Expected | Pass if |
|---|---|---|---|---|---|
| RS485-01a | 0.5 m | `python ../tools/bench.py rs485 --port COM6 --id 3 --cmd PING -n 50` | success %, mean/p95 ms | 100 %, ~3–8 ms | 100 %, p95 <20 ms |
| RS485-01b | 5 m | same | same | 100 % | 100 % |
| RS485-01c | 20 m | same | same | 100 %, latency unchanged (propagation is ns) | ≥99 % |
| RS485-01d | 50 m | same | same, plus corrupted count | still fine at 115200 if terminated | ≥99 %; log any corruption |

Latency should be **flat** with length — RS485 propagation is nanoseconds per
metre. If latency rises with length, the cause is retries/corruption, not
distance, and RS485-02 is where you find out why.

### RS485-02 — termination

CV: the longest cable you have (from RS485-01), 2 nodes.

| ID | IV setting | Command / action | Measure (DV) | Expected | Pass if |
|---|---|---|---|---|---|
| RS485-02a | both ends 120 Ω | bench.py ×50 | success %, corrupted | 100 % | 100 % |
| RS485-02b | one end only | remove one resistor, repeat | success %, corrupted | reflections start to bite on long cable | record |
| RS485-02c | none | remove both, repeat | success %, corrupted | worst case; short cable may still pass | record |
| RS485-02d | both, but stub 2 m off the middle | add a T-stub | success %, corrupted | stubs cause reflections | record |

This is the clean experiment for "do we actually need termination on **this**
installation" — with a length, a rate and a number.

### RS485-03 — node count and discovery

CV: terminated, shortest reliable cable.

| ID | IV setting | Command / action | Measure (DV) | Expected | Pass if |
|---|---|---|---|---|---|
| RS485-03a | 1 node | `#* PING` ×20 | distinct `@<id>` replies | 1 every time | 20/20 |
| RS485-03b | 2 nodes | `#* PING` ×20 | distinct replies, gap between them | 2; replies staggered ≈ id×20 ms apart | 20/20 complete |
| RS485-03c | 4 nodes | same | same | 4 | ≥19/20 complete |
| RS485-03d | 8 nodes | same | same, plus collisions | staggering (`id × 20 ms`) must keep them apart | ≥19/20; log collisions |
| RS485-03e | 8 nodes, adjacent ids | give them ids 1,2,3,4,5,6,7,8 | collisions | 20 ms spacing — the tightest case the stagger has to survive | log |
| RS485-03f | 8 nodes, spread ids | ids 1,50,100,150,200,240,245,247 | last reply arrives after | id 247 replies ≈4.9 s later — **the discovery timeout must be ≥5 s** | all 8 arrive |

RS485-03f is the sharp one: the stagger is `id × 20 ms`, so a **high id makes a
module look absent** to any host that gives up early. The result decides what
the hub's discovery timeout should be.

### RS485-04 — addressed vs broadcast

| ID | IV setting | Command / action | Measure (DV) | Expected | Pass if |
|---|---|---|---|---|---|
| RS485-04a | addressed, correct id | `#3 PING` | reply | `@3 PONG 3 <name> <type>` | exact |
| RS485-04b | addressed, wrong id | `#99 PING` (no such module) | reply, timeout | **no reply at all** — silence is the correct behaviour | no reply in 2 s |
| RS485-04c | broadcast non-PING | `#* SPEED 120` on a 2-node bus | replies; did both execute? | **no replies**, both modules execute | 0 replies, both changed |
| RS485-04d | broadcast PING | `#* PING` | replies | every module replies, staggered | all reply |
| RS485-04e | id 0 as broadcast | `#0 PING` | replies | treated as broadcast (`addr == "0"`) | same as 04d |
| RS485-04f | bad frame | `#3` (no command), `#` alone, `3 PING` | reply | `ERR bad frame …` from the bridge / silently ignored on the bus | matches COMMANDS.md |

### RS485-05 — command rate (throughput / saturation)

CV: 2 nodes, terminated, addressed `PING`.

| ID | IV setting | Command / action | Measure (DV) | Expected | Pass if |
|---|---|---|---|---|---|
| RS485-05a | 1 /s | bench.py `-n 50 --rate 1` | success %, p95 ms | 100 % | 100 % |
| RS485-05b | 10 /s | `--rate 10` | same | 100 % | 100 % |
| RS485-05c | 50 /s | `--rate 50` | same | half-duplex turnaround becomes the limit | ≥99 % |
| RS485-05d | 100 /s | `--rate 100` | same, plus lost | at 115200 a `PING`+reply is ~2 ms of wire time; the DE turnaround and the module loop add more | record the rate where loss starts |
| RS485-05e | saturation point | raise the rate until loss >1 % | that rate | **the bus's usable command rate** | report the number |

RS485-05e produces the single most useful number in this file: how many
commands per second the show can rely on.

### RS485-06 — frame length

| ID | IV setting | Command / action | Measure (DV) | Expected | Pass if |
|---|---|---|---|---|---|
| RS485-06a | ~10 chars | `#3 PING` | reply | ok | ok |
| RS485-06b | ~100 chars | `#3 POSE 90 90 90 90 90 90 90 90 90 90 T 1000` padded with spaces | reply | ok | ok |
| RS485-06c | 240 chars | `#3 SET NAME <220-char name>` | reply | ok — still under the 250-char buffer | ok |
| RS485-06d | 260 chars | same, longer name | reply | **line dropped** (`if (buf_.length() > 250) buf_ = ""`) — no reply | no reply; document the limit |
| RS485-06e | reply length | `#3 INFO` (status JSON is long) | full reply received? | the reply can exceed 250 chars — the **receiving side** must not have the same limit | JSON parses |

RS485-06d/e together answer "what is the largest thing we can safely put on the
bus, in each direction" — they are not the same number.

### RS485-07 — module id range

| ID | IV setting | Command / action | Measure (DV) | Expected | Pass if |
|---|---|---|---|---|---|
| RS485-07a | id 1 | `SET ID 1`, then `#1 PING` | reply | `@1 PONG …` | exact |
| RS485-07b | id 247 | `SET ID 247`, `#247 PING` | reply, and delay after `#* PING` | works; discovery reply ≈4.94 s late | exact |
| RS485-07c | id 0 | `SET ID 0` | reply | `ERR id must be 1-247` | exact |
| RS485-07d | id 248 | `SET ID 248` | reply | `ERR id must be 1-247` | exact |
| RS485-07e | duplicate ids | two modules both `SET ID 3`, then `#3 PING` | replies | **collision** — both answer at once, garbled | confirm and document |

RS485-07e is the failure mode an installation actually hits. Document exactly
what it looks like on the wire so it's recognisable later.

### RS485-08 — nong leader traffic on a shared bus (`link 1`)

Only for the nong series. A nong leader with `link 1` puts a `POSE … T <ms>`
frame on the bus for **every** pose it executes — while the host is also
talking.

| ID | IV setting | Command / action | Measure (DV) | Expected | Pass if |
|---|---|---|---|---|---|
| RS485-08a | link 0 | leader `CFG link 0`, host polls `#3 PING` at 10/s while a sequence runs | success %, p95 ms | baseline | 100 % |
| RS485-08b | link 1, peer set | `CFG link 1`, `CFG peer 5`, same sequence + same polling | success %, p95 ms, collisions | leader traffic + host traffic share the bus | ≥99 %; record latency rise |
| RS485-08c | link 1, peer 0 | `CFG peer 0` (broadcast) | same, plus: do other modules react? | `#*` reaches every module — a lift on the bus sees `POSE` and answers `ERR unknown cmd` | document the cross-talk |
| RS485-08d | fast sequence | a sequence with 80 ms steps, link 1 | frames/s on the bus, dropped host commands | worst-case bus load | report frames/s |

RS485-08c is the argument for always setting `peer` to a real id when more than
one robot shares the bus. Measure it rather than assuming it.

### RS485-09 — file transfer over the bus

| ID | IV setting | Command / action | Measure (DV) | Expected | Pass if |
