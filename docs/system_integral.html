What this is for

Reconize (E:\final_proj\mice\Face_Regonize) recognises faces. The rig should follow it: greet a known person by name with a move, answer questions aloud while the nong points the way, take questions only when somebody is standing there, let other Python programs drive the rig, and notice when that app updates.

It is never modified. Its own updater runs git checkout --detach, so anything we put in its folder would be wiped or would block its update. We only call it over HTTP, and we never read its SQLite file — it runs without WAL, so a long read would block its own writes.

Outside apps are generic from the start. One entry per program in config/partners.json: address, how to log in, where its events come from, how its fields map to ours, its folder to watch. Reconize is the first entry, not a special case — the second app is one entry and no code.

Decided, and not to be re-asked

Watch first, push later · their count is the truth · the start button comes last · the tile is called Reconize · the camera app becomes ESP32 camera · presence mode is opt-in and only gates asking questions, never the nong's own sequences or commands · an unknown person is never greeted with a guessed name · wording is per camera and editable on the screen · field changes are reported, never acted on by themselves.

What the review caught

Five rounds with Codex through claudex-loop. 22 findings, each checked against the real code before it was accepted. The ones that would have hurt:

  • Both passwords served to anyone on the WiFi — a file under apps/ is served with no login (main.py:3702-3715). Credentials moved.
  • A person's name went into SSML unescaped (tts.ps1:22-26) — a name with & breaks the speech, or injects markup.
  • A greeting would have started after Stop All. Stop now clears the queue.
  • Strangers never reach us from agent cameras (node_agent.py:285-290), so each source declares what it can report.
  • The show clock was never the audio problem — one sender per hub is.
