Firmware core — shared by all module types

One shared core, one build per module type. Nothing about wiring or identity is compiled in — only which module the board is.

Identity & configuration

One binary per module typenew

A board runs one module type, so it now carries one: pio run -e mice_nong, -e mice_lift, or -e mice_blank for a board that is not a module yet.

Every board used to carry every type — a humanoid flashed the lift's motor code, its RGB strip, its MP3 support and its web cards, with only a JavaScript check keeping them off the screen. That was 74.9% of the chip's flash on every board. A nong build is now 65.5% and does not contain the lift's page at all: the wrong controls are absent, not hidden, so no script bug can show them. The room this frees is what makes flashing over WiFi (which needs two copies of the firmware on the chip) possible later.

The source stays shared. One marker says which module type a card, a command or a block of code belongs to, and the build takes only its own.

The board still confirms its type

SET TYPE lift|nong|blank + reboot, from the Settings card or any channel. A binary only accepts the types it was built with, so SET TYPE lift on a humanoid build answers ERR unknown type (nong,blank) instead of booting a module that is not there.

Runtime pin map, stored on the board

Every pin lives in the board's own NVS memory, not in the source — motor, encoder, limits, RS485, SD, I2S and all 10 servos. Set from the website or with PIN <name> <gpio>. One firmware fits any wiring.

PIN VALID classifies every GPIO (ok / strap / input-only / flash / rgb) and reports pwm+adc+dac capability, so the picker can warn before you pick a pin that cannot work. The WS2812 data pin is the one exception — FastLED fixes it at compile time.

Settings that survive without an SD card

CFG <key> <value> stores settings in NVS and overrides module.yaml: encoder leds speed speed_mms stages stage_mm mm_per_rev counts_per_rev max_rpm counts_per_stage volume speed_dps max_dps link.

Name & bus address

SET NAME also renames the WiFi hostname, the .local address and the AP hotspot. SET ID 1–247 sets the RS485 address.

Connectivity

A bad network never stalls the robotnew

The WiFi code runs in the same loop as the servo interpolation, so anything that waits there would stop a joint mid-move — exactly when the venue's network is worst. The connect path is a polled state machine with timeouts: it tries, gives up, scans in the background, falls back to its own hotspot, and keeps retrying the real network in case it appears later. With WiFi set to OFF it does no radio work at all.

Even renaming the module defers its radio restart instead of waiting for it. QC fails if a blocking wait is ever added back.

Three WiFi modes

SET WIFI ON joins your network with hotspot fallback (default), AP always hosts its own hotspot, OFF disables the radio entirely for the fastest boot and USB/RS485-only operation.

The radio changes live — nothing needs a rebootnew

WIFI on its own answers one line saying exactly where the radio is: mode, state, which network it is trying, its IP and signal, its own hotspot name and how many modules are connected to it. WIFI ON|OFF|AP changes the mode on the spot, WIFI RETRY tries the stored network again without waiting for the 60 second clock, and WIFI SCAN lists the 2.4 GHz networks this board can actually see — which answers "why won't it join?" directly.

SET WIFI <ssid> <pass> now joins immediately too. It used to answer "reboot to apply", so correcting a mistyped network name meant power-cycling a module and leaving the arm wherever it stopped. The scan is asynchronous, so none of this can stall a joint mid-move.

Every module shares its WiFinew

A module in ON mode hosts its own hotspot all the time, including while it is connected to the show network. So a module parked out of router range can join a nearby module's hotspot and be reached through it, and a module you cannot reach any other way is always still there at 192.168.4.1 to be fixed. Previously the hotspot was dropped the moment the module got online, so it shared nothing.

The credentials you set on the module are always what gets tried first — the ones compiled into the firmware are only a factory fallback for a board nobody has set up yet.

A module that shares its WiFi answers a little slowerfixed

A module hosting its own hotspot and using the show network has one radio doing both, so it time-slices and occasionally answers late. Two things were quietly breaking because of it:

The hub lost modules that were online. Its network sweep waited 0.6 s per address; the lift answered that 7 times in 8, so the hub dropped it from the list on 2 scans out of 3 while it sat there working perfectly. The hub now sweeps fast to find anything new, then goes back and asks the addresses it already knows patiently. A module that has genuinely gone still disappears.

REACH failed most of the time over a shared hotspot — 1 of 6, while the far module answered the PC 6 of 6 throughout, so the far module was never at fault. It now retries within a bounded budget: 20 of 20, both directions. Over a direct module hotspot (one hop, no sharing) a single attempt was always enough.

Modules on a different subnet are found toofixed

The hub's network sweep only walks the PC's own /24, so a module on a different subnet was invisible to it however reachable it actually was. Seen on a dorm network: the PC on 10.94.163.x, both modules on 192.168.100.x, answering the PC perfectly — and the hub listed nothing at all.

The hub was plugged into both over USB the whole time, and a module's INFO carries its own IP. So plugging a module in once is now enough for the hub to find it over WiFi afterwards, whatever subnet it ended up on. Addresses already known are re-checked every scan regardless of subnet.

Name the moves in a sequencenew

The timeline showed 0 start pose and then 1, 2, 3 — which says nothing about what the show does. Each move now has a name you type straight on its chip: “wave”, “reach cup”, “bow”. The number stays, because that is what every message and warning refers to.

The name is saved with the project and written into the exported file as a comment — so every existing player still reads the file unchanged, the firmware needs no new step key, and anyone opening the YAML can see what each step was meant to be. Clearing a name removes it rather than storing an empty one.

Clicking a move previews it at that move's speedfixed

With a sequence set to 40 or 60 deg/s, clicking a move in the timeline still snapped the arm across at full speed. Two different jobs were sharing one path.

Dragging a slider should follow your hand, so the pose is sent with a time measured from the link's own round trip — deliberately quick. Clicking a move is not that: it should travel the way the move travels in the show, or what you are previewing is not what will happen. Now it carries that move's own time, taken from the played timeline, so a move after a suspended keyframe gets its re-timed value rather than the number stored against it.

QC checks the time that actually reached the module, not the editor's opinion of it — the editor's opinion was exactly what was wrong.

The crash check now warns instead of blockingnew

The collision check runs while you pose the robot, while you play, and before Run or upload. What changed is what happens when it finds something.

The 3D preview always plays. Watching where the movement goes wrong is how you fix it, so nothing stops you seeing it. Whether it also reaches the robot is a separate question, and it is asked only when a module is actually connected: you get one confirm naming the bad keyframes, with OK = do it anyway and Cancel = stop and fix it. Refuse, and the preview plays on its own while the arm stays where it is.

Before this, Run and upload were blocked outright with no way past — and the check works from your rig's dimensions, so a rig that does not match the real robot could call a perfectly safe move a crash and leave you stuck. Forcing is allowed because it is your arm and you can see it.

Play was the dangerous one. It warned that only the 3D preview would play — and then drove the real arm anyway. It said one thing and did another, on the single path where being wrong bends metal. All three routes now go through one gate.

Permission lasts for one action. Editing the timeline withdraws it, so a “yes, run it anyway” given for one movement never quietly covers a different one.

RELAX now relaxes every jointfixed

Nine servos went limp on RELAX and SHRUG stayed stiff. The loop was never wrong — it always covered all ten. Detaching a servo only hands the pin back to plain GPIO; it says nothing about what level the line settles at. On a pin with an internal pull-up the line then sits high, and a servo watching a permanently high line holds its position instead of going limp.

SHRUG is on GPIO 15, a strapping pin the ESP32 pulls up at reset. The other nine happened to settle low, so they appeared to work. RELAX now drives every servo line low itself — saying “no pulses” rather than hoping — which is correct on every pin, not only the lucky ones.

QC previously covered RELAX only as a command that interrupts a sequence. It now also checks that it reaches every joint, that a relaxed line is really idle, and that no per-joint loop quietly stops at the eight arm joints and leaves WAIST and SHRUG behind.

Playback is much lighterfixed

Studio lagged while playing and froze when you came back to the page. The cause was work, not logic. The joint slider row was rewritten on every tick — six properties per joint, sixty writes a frame — and two of those were the travel limits, which had not changed. Setting a slider's min/max makes the browser re-check and clamp its value, so those were the expensive ones.

On top of that, the show clock is called from both the animation frame and a timer, so the picture was being redrawn about 76 times a second on a 60 Hz screen. Together that was roughly 4500 DOM writes a second for a row that mostly had not changed.

Now a value is written only when it actually differs, the limits only when the rig changes, and painting happens once per animation frame. Time still advances on whichever timer fires — that is what keeps a hidden tab moving — only the painting is limited.

Dragging the timeline moves the real armnew

Scrubbing used to move only the picture. Checking one move without playing the whole show is the reason the scrubber exists, and a preview that moves while the robot stays put is the one thing you cannot check against. The arm now follows the scrubber, using the same path a slider drag does — so it carries the link's own round-trip timing instead of easing at the module's speed setting.

Nong Studio no longer leaks graphics memoryfixed

Studio could take the whole machine down after a while — not with an error, just a crash. That is the signature of running the graphics card out of memory.

Rebuilding the 3D robot freed its geometry but never its materials, and a fresh material is created for every mesh on every build. The robot is rebuilt on every rig edit, so tuning the rig leaked a material — and its compiled shader — on every change. Removing an object from the scene only drops the JavaScript reference; the buffers stay on the card until they are handed back explicitly. Twenty-five rebuilds now leave the counters exactly where they started, and QC measures it rather than trusting it. Textures are deliberately left alone: they are cached and shared between builds.

The viewport size watcher was also made self-limiting, so it can never re-trigger itself and spin the processor.

Move your whole setup to another PCnew

Everything Nong Studio remembers — your tuned rig, your saved default, the STL assignments, the panel width — lives in that browser on that PC. Tuning a rig on the workshop machine and finding the show laptop knows nothing about it is what this fixes. In Studio's Setup tab, under “Move your setup to another PC”.

By file: Export writes one JSON file; copy it across and press Import. It is applied straight away and kept in that browser's cache.

Over the network: on the PC that has the setup press Share; on the other PC press Find PCs, pick it from the list, press Get. The search looks for other mice hubs on the same network, so no address has to be typed — though you can type one if the search cannot see it.

The transfer goes through your own hub rather than straight from the browser: a page served by one hub is not allowed to read another hub's response, so the hub does the fetching and hands it back. Sequences and projects are deliberately not included — those are already files on the hub. Neither is the zero-calibration login, which is per machine.

Shrug: a 4-bar linkage is not a see-sawnew

One servo drives the linkage that lifts both shoulders, so there is only ever one angle to command. But a 4-bar does not lift the two sides by the same amount, and the ratio changes across the travel. The preview rocked a single rigid bar, so it always drew the shoulders as exact mirror images — which is not what the robot does. The robot was right the whole time; the picture was wrong.

Measure it once, in the rig setup: set SHRUG to a few angles and note how far each shoulder actually rose, in millimetres, up positive. Two rows is the minimum; more rows describe the curve the linkage really follows. The preview then places each shoulder at its own height and stops rocking the bar, so the rotation is never counted twice on top of your measurement.

Measured beats computed here: the real linkage carries horn spline offset, bearing slop and mounting error, none of which the CAD model knows about. Leave the table empty and nothing changes — every rig saved before this keeps looking exactly as it did. Past the ends of your measurements the value holds rather than extrapolating a shoulder off into space.

Only one thing drives the servos at a timefixed

The module keeps a sequence and plays it on its own clock — that is what lets a show survive this page closing. But it meant the module could still be running when you came back, and pressing Play then had the browser streaming poses as well: two clocks on one robot, the arm fighting itself. Worse, Stop only stopped the browser, so the servos kept moving from the module's own sequence.

Play, Pause and scrubbing now all stop the module first. Taking control takes it completely.

A show keeps running when you leave the pagefixed

A hidden browser tab has its animation loop stopped and its timers slowed to roughly once a minute. No trick changes that reliably. The sequence ran at the wrong speed, or simply stopped and sat still until you looked at the page again.

So Studio stops trying to be the clock. When a show is playing and you switch away, the whole sequence is handed to the module, which plays it on its own 50 Hz timer — it keeps going with the browser minimised or closed completely, and it interpolates with the same formulas the preview uses, so the motion is identical rather than merely similar. Coming back, the page says the module is running it. Press Stop to end it.

Coming back also used to hang the page for a moment: the play head was advanced by the whole time you were away in a single step, so the pose jumped across the show and every joint was re-sent at once. One tick can no longer advance the show by more than a frame.

The USB lagfixed

The hub waited up to 80 ms before every command, to let a half-written log line finish. That cost is paid on each command and is worst exactly when the board is chatty — which became normal once every module started hosting a hotspot. On live pose streaming (about 30 commands a second) it was most of the delay, and the arm visibly trailed the sliders. The blank-line reply marker already tells a reply apart from a stray log line, so the wait was doing nothing and is gone.

The 3D view no longer covers the settingsfixed

One wide row in the side panel could push the panel wider than its 320 px, which silently shrank the 3D viewport — but nothing told the canvas to resize, so the render spilled over the settings and covered the controls. The panel is now a fixed track that wide content scrolls inside, and the canvas watches the viewport element itself, so it follows every size change: dragging the splitter, switching tabs, a scrollbar appearing.

One design system across every pagenew

The hub, this help page, the RGB page, Nong Studio and the module's own website read their colours, radii and spacing from one file: shared/web/mice.css. They used to hold six copies of it, each one commented “the shared design system” and none of them shared — they had already drifted into three different corner-radius scales and four names for the same grey caption.

Every page links it at /mice.css. The board serves that same URL itself: the stylesheet is compiled into the firmware, so a module looks the same whether you reach it over WiFi or through the hub over USB. QC fails if a page declares its own tokens, hardcodes a colour that is already a token, forgets the link, or if the copy in the board's flash is not byte for byte the shared file.

Dark stays the permanent default: the show area is kept dark and a bright screen spills light into the event.

Flashing says which board, and which PCnew

Overwriting firmware cannot be undone from this screen, it takes about a minute, and the board is usually in someone's hands across the room. The old question named a COM port or an IP address — neither tells you which of the boards in the room you are about to overwrite.

The confirm now names the board (its name, its id and the type it runs now), what it will become and whether that is a change, how it is reached (this PC's cable, or WiFi), and which PC is doing it, by name. That last one matters because several machines at a venue run this same hub on the same network, so being on the wrong browser tab is the easy mistake.

Cancel is the prominent button and the one under your thumb; overwriting is styled as destructive and has to be reached for. Escape cancels. QC clicks Cancel and then checks the hub, not the page — a confirm that closes while the write has already started would be worse than no confirm at all.

The hub asks for a password before it does anythingnew

The hub listens on every network connection so a phone on the same WiFi can reach it. Until now that also meant anyone on that WiFi could drive the servos or reflash a board. Now anything that changes something needs a login.

Looking stays free. The module list, the status of every board, this help page and the pages themselves all work with no password — someone checking whether a board is alive should never meet a password box.

Two details that are easy to get wrong. First, the rule is not “GET is safe”: /api/usb/cmd is a GET that moves the arm, so the gate is a list of what changes something, not a rule about the kind of request. Second, stopping is never gated — a password prompt while an arm is about to hit someone is a safety failure, so starting a show needs a login and ending one never does.

On first run the hub prints a generated password in its own window, on the PC. It is never shown on a page and never sent over the network, so seeing it means standing at the machine. It is stored hashed, five wrong tries locks that caller out for a minute, and a module on another PC needs a login on that PC too.

One line per log, one writenew

The board writes its log lines to the same port it answers commands on. A log was printed in two steps — the text, then the line ending — so a WiFi event, which runs separately, could land between them and stick its message onto the end of a reply. On the bench that looked like OK joining lift-test now (WIFI for progress)[wifi] disconnected, reason=8, and the PC read the whole thing as the answer.

Every log now goes through one helper that builds the line and hands it over in a single write, which cannot be split. The subsystem names — boot, sys, wifi, sd, seq, ota, cam — live in one list instead of being typed at 36 places, a long line is cut with a visible ... rather than lost, and a log can never contain a line break in the middle, which would have looked like a second reply.

Keyboard and motionnew

Every page now shows a visible focus ring when you tab through it — three of the four had none — and every page respects prefers-reduced-motion, so animations stop for anyone who has asked their system to stop them. Touch targets are at least 36 px wherever the pointer is coarse.

The hub tells the truth when it cannot reach anythingfixed

A failed scan used to replace the module list with the words "scan failed". Now the hub keeps the modules it last actually found, marks them plainly as old (“showing what was found 40s ago — these may no longer be there”), and offers a Try again button. The list also carries a quiet “checked just now” line, so you never have to wonder whether the page is frozen.

A control panel that goes blank when the network hiccups is broken however good it looks; one that keeps presenting old robots as if they were still there is worse. QC drives this for real — it loads the hub, breaks the scan endpoint, and fails if the list blanks, if the data is not marked stale, or if there is no way to retry.

Groups: which modules are allowed to linknew

A module belongs to a group — your installation. Its own hotspot password is derived from the group name, so every module in one group shares it automatically and nothing has to be typed twice.

That is what makes automatic linking safe. With no venue WiFi a grouped module scans, finds a neighbour's hotspot and joins it without ever having met it, because the only hotspot it can actually get into is a group-mate's. Two companies working the same site each let their own modules find each other, and neither can touch the other's. An ungrouped module never goes hunting: it would be using the shared built-in password, which proves nothing about who owns the board.

Set it in the hub's Network tab — tick the modules that belong together and name the group — or with GROUP <name> on any channel.

A cold start with no WiFi used to strand every modulefixed

A neighbour was only recognised by a name the module had already seen, and a module that just booted has seen nobody. So with the venue network down, every module sat on its own hotspot unable to find any of the others. Found by pulling a module's USB cable and running it from a charger. Grouped modules now recognise each other on a cold start.

A weak link moves to a stronger neighbournew

Falling back only when WiFi fails misses the case that actually hurts at a venue: a module far from the router still connects, just badly — commands arrive late and the show stutters. Signal strength is now checked too. If the show network is weak and a neighbouring module's hotspot is clearly stronger, the module joins the neighbour and is reached through it.

It comes back once the show network is properly good again, not merely less bad. The two thresholds are deliberately different: with a single one, a module sitting near the boundary flips between networks forever, dropping its link each time — which at a show looks exactly like the robot randomly freezing.

WIFI reports via="<module>" whenever a module is leaning on a neighbour, so it is never a mystery. The rule is a pure function unit-tested on a PC, because a real −80 dBm signal cannot be made to appear on a bench.

Which WiFi a module uses, and how to get backnew

Credentials set on the board (SET WIFI, stored on the chip) always win over the ones compiled into config/conf_network.h — those are only the factory default for a board nobody has set up yet. Both currently point at the same network.

WIFI CLEAR forgets what was set on the board and goes back to the built-in one, immediately. Without it a module could only ever be moved from one named network to another, so a board pointed at a bench hotspot had no way home short of a reflash.

One USB cable runs the whole installationnew

The usual situation at a venue: there is no usable WiFi. Plug the PC into any one module and let every other module join that module's own hotspot. The hub lists them under the cable and each one gets its normal buttons — its website, Nong Studio, file upload, sequences — even though your PC has no route to it at all.

Internally the hub addresses them as usb:COM11@nong: over this cable, then through it to the module named nong. It is a name, not an address, so it keeps working when the hotspot hands out a different one. Nothing else in any page changed — only the device string.

The same form works over WiFi (wifi:10.0.0.5@nong) when the module you can see is the one with the good signal.

Reach a module through another modulenew

A module parked out of router range joins a nearby module's hotspot — but it is then on that module's private network, where the PC has no route to it. So the module it joined forwards for it. PEERS lists what a module can see, and REACH <ip|name|id> <command> runs a command over there and hands back exactly what that module answered:

PC → USB → lift-test → its own hotspot → nong
REACH nong PING → PONG 67 nong nong

It is the same shape as the RS485 bridge (#3 GOTO 2) — one command in, one reply line out — so the hub's device routing and the module website's console needed no changes at all.

It is for finding and configuring a module, not for driving one during a show: it waits up to 800 ms for the far module, so it answers ERR busy rather than reach through while this module is mid-move and stop a joint dead. In a show, address the module directly or use RS485.

A reply is never a stray log linefixed

The module logs to the same serial line it answers on, and the two used to collide in three different ways. All three were found on the bench with two boards reconnecting, and all three are now covered by QC:

A half-eaten log line came back as the reply. The hub cleared the buffer before each command, which could cut a log line in two. The orphaned tail had no [tag] on it, so the log filter did not recognise it — SET WIFI answered "Hz-only network — ESP32 is 2.4GHz only)".

A log line was glued onto the end of a reply. Serial.println() is two writes — the text, then the newline — so a WiFi event on another task could land between them. The board now writes each reply as a single "\n" + reply + "\n", which no other task can get inside.

Every reply came back shifted by one. During a reconnect, 49 of 60 commands returned the previous command's answer. That leading blank line is now the marker the hub looks for: a real reply always has one in front of it, an orphaned tail never does. The same hammer test on real hardware now scores 50 of 50. A board running older firmware still works — without the marker the hub falls back to the old behaviour.

RS485 bus — many modules on two wires

Address any module with #<id> <command> and it answers @<id> …. #* PING takes a census of the whole bus. Modules bridge # lines onto the bus, so one module's USB port reaches every other module behind it.

Accounts stored on the board

The website's Setup gate is backed by real accounts in NVS (default manny / 12345678). AUTH, plus USER LIST|ADD|DEL|PASS — user operations require valid credentials. The raw command channel stays open for scripts and RS485.

Storage & playback

SD card files over any channeloptional card

List, upload, download and delete SD files over HTTP or the text protocol — FILES, FBEGIN, FDATA, FEND, FREAD, FDEL, in base64 chunks small enough for one RS485 frame. Folders: /music, /moves, /data.

YAML sequence player

MOVE <file> runs a sequence from /moves; steps that travel wait for arrival, others fire and continue. MOVE STOP ends it.

SET TYPE lift

Lift module

A rack-and-pinion lift with staged positions, an LED strip and a speaker.

Staged travel with real distances

GOTO <stage> auto-homes first if the position is unknown. UP/DOWN run to a limit switch, HOME seeks the bottom and zeroes the encoder, STAGE? reports where it is.

Speed in real units, not PWM

SPEED 0.2 MS takes m/s (or MMS for mm/s) and maps it to PWM from the actual mechanics — module-2 rack with a 25-tooth pinion gives 157.08 mm per revolution. TIME? estimates any move live.

Works without an encoderoptional

CFG encoder 0 and the lift runs limit-switch to limit-switch: endpoint stages only, open-loop speed mapping, and the web UI hides what no longer applies.

RGB strip

RGB r g b, RGB BRIGHT, and effects solid rainbow chase breathe off. A dedicated hub page adds a mode that follows the PC speaker.

Audio

PLAY <file> plays mp3/wav from /music over I2S, PLAY STOP ends it, VOL 0–100 sets level.

SET TYPE nong

Nong module — humanoid upper body

Two arms and a body: 10 logical joints driven by 10 servos, from one ESP32. Every angle is a joint degree — the physical joint — so poses stay valid no matter what servo or gear is fitted.

Joints
#NameWhat it moves
1 / 2L_SH_P / L_SH_RLeft shoulder — pitch and roll (a universal joint, 2 servos)
3 / 4L_EL_P / L_EL_RLeft elbow — pitch and roll
5 / 6R_SH_P / R_SH_RRight shoulder — pitch and roll
7 / 8R_EL_P / R_EL_RRight elbow — pitch and roll
9WAISTYaws the whole upper body so nong can look to the side
10SHRUGRocks the shoulder bar like a see-saw — one shoulder up, the other down (~6°)
Motion

Whole-body and single-joint moves

POSE takes all 10 angles, - keeps a joint where it is, and an old 8-value pose still loads. JOINT WAIST 60 moves one joint by name.

Smooth interpolation with an honest time floor

Every move eases in and out over a duration T. A T shorter than the servos can physically achieve is raised, per joint, so the interpolation never "finishes" before the real arm arrives. The editor enforces the identical formula while authoring.

Hold, freeze and go limp

STOP freezes mid-move at the pose reached. RELAX unpowers the servos so you can pose the arms by hand; ATTACH powers them again holding the current pose. HOME returns to the neutral pose.

Calibration — all per joint, all live, all persistent

Set zero by hand

SETZERO declares wherever the arms are now to be home. Trim absorbs the offset, so the arm does not move when you run it.

Per-joint servo, gear, pulse, travel and frame rate

GEAR (pinion:gear), PULSE (µs range + max °/s), RANGE (servo travel 180/270°), RATE (frame rate Hz), LIMIT (joint travel). Nothing is hard-coded for the whole arm — a 270° shoulder next to a 180° elbow is fine.

Presets via SERVO <joint|ALL> <type>: mg90s, pdi1181mg, tiankong35, generic180, generic270.

servo travel ≠ joint limits. servo_range is how far the servo turns — a property of the part you bought. joint_min/joint_max is how far the joint may turn — a property of your mechanism. Poses are always joint degrees, so fitting a 270° servo is a one-number change and every saved sequence keeps working.

Calibration survives a power cycle — with or without an SD cardfixed

Every change is saved twice: to the chip's own memory always, and to /data/nong_cal.yaml as a readable copy when a card is fitted. So a board with no card keeps its gear, limits, pulses, travel, rate and zero instead of coming back on the factory defaults every time you unplug it.

At boot the card file is applied first and the chip copy second, so the chip copy wins — it is written by every calibration command whether or not a card is present. CAL reports which copies exist; CAL CLEAR forgets both and a reboot returns to the defaults.

Scaling out

Split the humanoid across two boards

Set servo_pins so each board drives only its own joints (-1 for the rest). The leader gets link 1 + peer <id> and repeats every move to its partner over RS485 with the resolved duration, so both move as one robot. Every board tracks all 10 angles, so status on the leader always shows the whole humanoid.

served by the board — and by the hub over USB/RS485

Module website

One site per module, identical over every transport. The hub serves the board's own HTML with a transport shim, so a board with no WiFi shows the same page over a cable.

Three tabs, not one long pagenew

Sending the rig is 5x fewer commandsnew

Send rig to robot used to push five commands per joint — fifty round trips, about 1.6 s. The new JCFG command carries a joint's whole setup in one line, so it is ten. Only joints that actually differ are sent at all, and a board older than JCFG automatically gets the individual commands instead.

The board says what it can donew

A new module type therefore shows the right controls without the site being taught about it. A board running older firmware sends no capabilities and still renders correctly.

Commands declared oncenew

The board compiles it into a table for its own HELP, and QC checks it both ways: a declared command must have a handler, and a handler must be declared. It found two commands (PINS, PINS?) that had existed undocumented.

Nong Studio — pose & sequence editor

A 3D editor for the humanoid. Build poses, chain them into a timeline, watch the real robot follow along, and export sequences the module plays from its SD card. three.js is vendored — no CDN at runtime.

The old Movement/Setup split put the robot link, the SD card and the zero calibration all under Movement, so posing meant scrolling past things you touch once.

Sliders, gizmos and inverse kinematics

A slider per joint, clamped to that joint's own limits. Drag the 🟢 wrist ball for 4-DOF whole-arm IK, or the 🟠 elbow ball for shoulder-only IK. Gimbal rings follow each joint's configured axis and tilt.

Flat plane viewsnew

Front, Back, Left, Right, Top and Bottom are true orthographic views — parallel edges stay parallel and nothing looks bigger for being nearer, so Shift+dragging a joint in that plane matches exactly what is on screen. The iso/free view keeps perspective, where depth is the point. Switching between them never moves the camera.

Live XYZ readout

Joint positions in millimetres, origin at the torso centre.

Collision checking

Arms against torso, head and each other, sampled along the whole path — not just at keyframes. Offending keyframes turn red and Run/Upload are blocked until it is fixed.

Mirror and neutral

Mirror a pose left↔right, jump to the neutral pose, or save the current pose as the neutral.

Timeline

Keyframes with time and hold

Each keyframe carries its move duration and a hold. Times auto-calculate from show speed and are floored per joint by the slowest servo in that move — the same formula the firmware uses. Any keyframe's time can also be typed in directly, which is how you make one move slower than the rest.

Speed per sequence, and per movenew

Show speed (°/s) is saved into the sequence file as its first step and restored when you re-edit it, so each sequence keeps its own pace. Change it and every keyframe time is recalculated.

Each keyframe also has its own °/s box — leave it blank to run at the sequence's speed, or set it to make that one gesture slower or snappier. The file sets that speed before the move and puts the sequence speed back after, so the rest of the show is untouched. Speed and time are two views of the same thing: set a speed and the time follows, type a time and the override is dropped.

Because each file sets its own speed at the start, a chain hands over cleanly — a fast sequence following a slow one runs at its own speed instead of inheriting the previous one's.

Suspend a keyframe instead of deleting itnew

The ● button on a keyframe chip suspends it: it stays in the timeline to edit, but is skipped when playing, exporting and uploading — so you can try the sequence without one move while you check something else, then switch it back on.

Skipping keyframe 2 of 1–2–3 creates a new, longer move 1→3. Its time is recomputed at the speed that applies — keyframe 3's own °/s if it has one, otherwise the sequence speed — so the arm covers the extra distance at the pace you asked for instead of lunging. Suspending can only ever slow a move down: a time you typed yourself is kept if it is already longer.

The crash check re-tests that new path, and the suspended pose never reaches the robot or the exported file.

Play, scrub and loopfixed

Preview in 3D, or with live ticked drive the real robot: keyframe 0 first, then each segment with its exact duration. A hold is a real pause between the moves. Pause sends STOP to freeze the arm where it is, and resuming asks only for the time still left in the segment.

Let the robot run the show on its ownnew

A browser stops its animation clock in a hidden tab, so a sequence driven live from Studio freezes when you switch to another tab or app. Press Send to robot then Run on robot instead: the module plays it from its own clock and you can close the browser entirely.

This used to need an SD card. Now a board without one keeps the sequence in memory (up to 8 KB, until it reboots) and plays it just the same — the editor is unchanged, the board decides where it lands.

Robot-side playback is also more accurate, not less: the module interpolates every move on its own 50 Hz clock, so timing does not depend on the browser or the link. Tick monitor to watch the real robot in 3D while it runs.

While playing live, Studio now holds a silent audio track and drives the clock from a timer, which keeps most browsers from throttling a background tab — best effort, and no substitute for running it on the robot for a real show.

Monitor mode — the model follows the robot

The 3D rig animates from the robot's real joint angles, and the status line shows which sequence is playing and how long the current move has left. Use it to watch a run started from the SD card.

Getting moves onto the robot

Export, upload and re-edit

Export /moves YAML with an explicit T on every step so linked boards stay in sync. Upload straight to the robot's SD card, or re-open a saved YAML — local or downloaded from the robot — and keep editing.

Many sequences on one card

The card holds as many /moves/*.yaml as fit. The Robot SD card panel lists them all with ▶ Run, ✎ Edit and delete on each, over WiFi, USB or RS485 — and the module's own website has the same list in its Sequences card. Name each export in the sequence-name box to keep them separate.

Chain one sequence into the nextnew

The then run… box writes next: into the file, so when it finishes the module starts that one by itself — a show built from short files that can each be run and edited on their own. The box offers the sequences already on the card.

It applies only when a sequence actually ends, so loop wins over it. Chains stop after 16 files, so a file pointing back at itself cannot run forever, and MOVE STOP ends the whole chain.

Camera modulenew

A third module type: an ESP32-CAM running the same firmware core as the lift and the humanoid — same identity, same commands, same website, same RS485 address, same update over WiFi. Build it with pio run -e mice_cam, or flash it from the hub like any other board.

Take a picture on its Control card shows one frame; the live view tick box refreshes it once a second. SNAP <name> saves a picture to /photos on its SD card. CAM reports and changes the sensor: CAM SIZE vga, CAM QUALITY 12, CAM FLASH ON (the white LED), CAM VFLIP 1 and CAM HMIRROR 1 for a camera mounted upside down or behind glass.

It can never also drive a servo. The camera and the on-board SD card use every usable pin on that board, which is exactly why it is a module type of its own. Its pins are fixed in the firmware rather than set on the Hardware pins page — they are etched onto the board, so "changing" one could only break the camera.

The live view is a stream (/api/cam.stream), not one request per picture: about 19 frames a second at 320×240, where repeated stills managed 7 and the original one-second timer managed 1. Only one person at a time can watch — the board has four connections in total, and a viewer holds one for as long as the picture is on screen. Untick live view to give it back.

The picture is HTTP (/api/cam.jpg), never a command reply: a JPEG is far too big for the one-line channels that RS485 and USB serial are. If the camera does not start, the card says so — it is almost always the ribbon cable not seated, or a 5V supply that cannot hold the current.

Update a module over WiFinew

It asks which firmware to send. The list is whatever this PC has built, with the board's current type marked and preselected — so the usual case is two clicks, and the unusual one is possible: picking a different type turns that board into another kind of module without finding a cable. When you do that the hub finishes the job, because a board flashed with a different type still has the old one in its own memory and would come back as blank: it waits for the module, sends SET TYPE, and reboots it once more.

It all happens on the Firmware screen. A module on the network appears there with ⚡ Write over WiFi — no cable, no reaching behind the set. The module's own row still has a ⚡ firmware… link, because the row is where you notice a board needs updating; it takes you to the one screen that does the writing.

A failed update cannot brick a board. The chip has two firmware slots (1.875 MB each) and the update goes into the one that is not running. If the WiFi drops, the PC walks away, or the image is bad, the board simply keeps booting the firmware it already had. Ask a board where it stands with OTA — it answers running=app0 size=1294617 target=app1 room=1966080 free=671463.

It is refused while the module is moving or playing a sequence — writing flash stalls the servo loop, and a reboot in the middle of a show is worse than an update that waits. Stop it first (or add force=1 if you mean it).

The first update still has to arrive by cable: a board running older firmware has no /api/ota to receive it. Flash it once over USB, and every update after that can be over the air.

Flash a board from the hubnew

Open Firmware. It lists every module type this PC has built, and under each one every board it could write it to — this PC's cables, boards on the WiFi, and cables on other PCs running the same hub. Pick the firmware, pick the board, confirm, and the hub writes it: no PlatformIO, no command line. Cables where nothing answered are listed too, which is exactly when you need this.

A type that has not been built is still shown, with the reason and the exact command that fixes it — so a missing lift looks like something you can do, not like something broken.

The hub owns every cable and shares it between its pages, but esptool cannot share. So for the length of the flash the hub gives that port up completely: it stops playing a show on it, closes the handle, and refuses to reopen it until esptool is finished. That is what all the old port is busy failures were.

It flashes what is on this PC: pio run -e mice_nong (or mice_lift) has to have been run at least once in code/firmware. If it has not, the page says so and names the command instead of offering a button that cannot work. The board keeps its stored id, name, WiFi and pins — those live in its own memory, not in the firmware.

If the board does not answer, hold its BOOT/IO0 button as the flash starts, and check the cable is a data cable. The message says so too.

The board's page admits when something failednew

Four things on the module's own website used to fail quietly and leave the page showing a state the board was not in. Each now says what happened:

• Changing a password signs you back in, and if that fails it says so — before, Setup opened on a dead session, with every card visible and every action behind it refused.
• A board that has never had a password chosen asks for one. If the board's answer cannot be read, it asks anyway: being prompted once too often is recoverable, and a prompt that turns itself off is not.
• Log out tells the board, and admits it if the board did not confirm — a logout that only forgets locally leaves the cookie working for whoever sits down next.
• A file list that could not be read says so instead of showing an empty dropdown, which already means nothing on this card.

Addresses and ports are hidden until you asknew

An IP address tells you nothing while everything is working, and it was on every row in the same grey as the name. Settings → Show technical details brings back the addresses, the cable ports and the signal strengths, and the choice is remembered in that browser.

Always shown, switch or no switch: the name, the type and the module number. The number is not trivia — it is how a module is addressed on the RS485 bus, and how two identical arms on a shelf are told apart.

It is one rule in the shared stylesheet (.tech), so a new screen marks a detail as technical and it follows the same switch — nothing to wire up and nothing to remember.

One board is one row, however it is reachednew

A module plugged into this PC and on the WiFi used to appear twice, as two robots. The two rows were not even equivalent: one drove it down the cable and the other over the air, so which copy you happened to click decided how the arm moved. Now it is one row, and it says every way the board can be reached — reachable on COM9 and over WiFi.

The hub matches boards on the chip: the ESP32's own MAC, which the board now reports in INFO and /api/status. It is the only identifier on a board that nobody can change — the id is a byte someone sets, the name is typed, the type is chosen.

That matters in the direction people do not expect. Two different boards out of the same box share a default id, and merging on the id would show them as one robot — a command meant for one arm going to the other. So without a chip (older firmware) the id is used only together with the type, and a board that reports a chip is never merged with one that does not.

Open the hub on a phone: a QR, and a namenew

Network shows a QR of this hub's address. Point a phone camera at it and the phone opens the hub — no number read across a room, no 192.168.137.1 typed as 192.168.13.71. The address is printed beside it for anyone working over a remote desktop.

The QR is drawn by the hub itself, with nothing installed: the encoder is part of the program. It is redrawn every time you open Network, because a laptop that moves between a venue WiFi and its own hotspot gets a new address, and a QR of the old one sends the phone nowhere.

There is a name as well: http://mice.local:9203/, answered by the hub over multicast DNS, which phones, Macs and Windows already speak. A name does not change when the address does.

Both exist because either can fail. Many venue networks block multicast between clients, and then no name resolves — the QR still works. If another program on this PC already holds the mDNS port, the page says so plainly and shows only the address, rather than printing a name that answers to nothing.

Flash from a PC that never built the firmwarenew

At a venue there is usually one laptop with PlatformIO on it and several without — and the board is plugged into whichever machine was nearest. So the image travels, not the command: Firmware lists boards on other PCs' cables as ⚡ Write over the cable on that PC. This PC sends the firmware there, and that PC writes it over its own cable. esptool only ever runs on the machine holding the board.

That PC has its own accounts, so the confirm asks for a login on it. It is used for the one request and not stored: no hub ever holds another hub's password.

Progress comes back from the machine doing the work, through this hub, because a browser cannot ask another hub directly. When the write finishes, a board that is becoming a different type is named along with the one command that finishes the job there — this PC has no route to a board on someone else's cable.

The hub keeps the show runningnew

Press Play and the hub — the Python program, not the page — sends the moves. Switch tabs, minimise the window, open something else: the rehearsal keeps going, because nothing throttles a native process. The page is only the picture.

This is the missing middle clock. A browser cannot be fixed for it: a hidden tab has its animation stopped and its timers slowed to about once a minute, by policy, in every browser. Which clock you want depends on the job:

USB direct (Web Serial) is the one exception: the browser holds that port itself, so the hub cannot reach the robot and the old behaviour stands — the show is handed to the module when you leave the page.

Only one thing drives the robotnew

The module plays a sequence on its own clock, and Nong Studio can send poses down the same cable at the same time. Both drove the same servos: the moves overlapped, the arm fought itself, and Pause in Studio stopped only the browser while the module carried on.

Now any command that moves the robot — POSE, JOINT, HOME, STOP, RELAX, ATTACH (and UP/DOWN/GOTO on a lift) — stops the sequence the module was playing, and the reply says (sequence stopped) so nothing loses track. Whoever moved the robot last owns it.

Settings do not interrupt a show: SPEED, LIMIT, SERVO, RANGE and every question keep it running, so you can tune a sequence while it plays. When Studio connects to a module that is already playing, it now says so instead of leaving you to guess.

A fake robot, so nothing needs hardware

A stand-in serial module with one exclusive port — a second open fails exactly like Windows, which is what proves the hub shares a handle. It can also play dead to reproduce a replugged board, and records every command with the time it arrived.

The rule that makes a check worth writing: break the fix and watch the check fail. A check that passes both before and after guards nothing.
