Nong Studio — pose & sequence editor

A 3D editor for the humanoid. Build poses, chain them into a timeline, watch the real robot follow along, and export sequences the module plays from its SD card. three.js is vendored — no CDN at runtime.

The dummy: pose the robot by handnew

The dummy is a second module type (mice_dummy): a copy of the nong with the same 10 joints and a potentiometer on each instead of a servo. It sits on the same RS485 bus with its own bus id (or its own USB / WiFi). In Studio's Robot tab, the Dummy card connects to it and offers: Studio follows the dummy, Studio + real robot follow the dummy (the robot's own limits and speed still apply), + Dummy pose as new move, Use dummy pose for selected move and Robot → selected move. Pick Simulated to try all of it with sliders and no dummy built. Pot pins, direction, travel, limits and zero are set on the dummy's own module page (Setup → Dummy calibration). Tested against the QC fake only.

Posing

Five tabs, grouped by what you are doingnew

Pose (joints, XYZ, view) · Sequence (timing, the robot SD card) · Shows (several sequences in a row) · Robot (link, module config, zero calibration) · Setup (rig, model, clothes). The old Movement/Setup split put the robot link, the SD card and the zero calibration all under Movement, so posing meant scrolling past things you touch once.

Nothing moved in the page itself — only what is on screen at once — so every saved project, link and shortcut behaves as before. QC fails if a card ever ends up on no tab, which would hide a feature completely.

Shows — several sequences in a rownew

A show is a list of saved sequences played one after another: greeting, then a wave, then byebye. Open the Shows tab, add saved sequences in the order you want them, set a pause after any of them in milliseconds, name the show and press Save show. ▶ Run on robot hands the whole thing to the hub, so it keeps going with the page closed; ⏹ Stop ends it from anywhere.

⇪ Save to robot puts the show on the robot's own card as one file, <show name>.show.yaml. The robot can then play it by itself, with the hub and the computer switched off: pick it in the robot's list of sequences (Robot tab, or the robot's own page). It is the same run as ▶ Run on robot — the same moves, pauses and music. A very long show may not fit in the robot's memory; you are told before anything is sent. Change the show, then send it again.

A show only stores the sequence names, never a copy — so one greeting can sit in ten shows, and editing the greeting changes all ten. Shows are small files in nong/main_python_set_nong/shows/ you can also write by hand. Deleting a show moves it to shows/.deleted rather than erasing it, and never touches its sequences. A show naming a sequence that is gone refuses to start and says which step is wrong, instead of playing half of itself.

A show runs straight through, and can repeat a sequencenew

One sequence now runs straight into the next, with no gap. There used to be one, and it looked like the robot had stopped: every sequence begins with its start pose, timed for travel from wherever the robot happened to be — yakyai.yaml asks for 3273 ms — so in a chain the arm stood almost still for three seconds between sequences. That first move is now timed from where the arm really is, at that sequence's own speed, so two sequences that end and start on the same pose hand over instantly. The only thing that makes the robot wait is a pause you typed.

Repeat beside each sequence plays it again, in whichever way you think about it: repeat × times (3 times, 4 times) or repeat for seconds (30 s, 60 s). Seconds never cuts a pass in half — it starts another whole pass while the time is still under the target, so 60 s of a 22 s sequence is three passes. A sequence far too short to fill the target is refused, by name, instead of building a list nothing can stop.

Run a sequence for exactly so many secondsnew

The third repeat setting, run for exactly … s, is for a show on a timetable — music, a slot in a programme, anything the robot has to stay in step with. The sequence gets exactly that long and no more. If it would run over it is cut wherever it has got to; if it is shorter it repeats to fill, and the last pass is cut too.

The cut is not a stop. Whatever time the cut frees is spent travelling into the next sequence's first pose, so the arm leaves early, is already on its way during the freed time, and arrives exactly on the deadline. The next sequence starts on time and there is no join to see.

The cut always lands on a keyframe, never inside a move — stopping half way through one would leave the arm at a position nobody chose. A pause you set on the item counts inside its budget rather than pushing the deadline out, and an item at the end of a show holds its last pose to length, since there is nowhere to travel to. Repeat for seconds is the gentler cousin: it never cuts, so it runs a little over.

On the time bar that travel is drawn as the end of the cut sequence, labelled one → two, and the next sequence's name starts right on the deadline — 42 s reads 42.0 s on the ruler. The seconds are counted from the show's first pose, the same place the time bar starts; the robot's walk to that first pose, from wherever it was standing, comes before the clock and belongs to no sequence.

The time bar and the robot keep the same timefixed

A show could reach a point on the robot a few seconds later than the time bar said (49 s on the bar, 52 s on the robot). Two things added up: the hub waited for each move after the robot had answered, so the cable's answer time was added to every move; and a move between sequences could be asked for faster than the robot allows, so the robot quietly took longer. Now the hub keeps one clock for the whole show, and every move is planned at no less than the time the robot will really take — with the robot's own speed limits, the ones in Timing.

A gentler move between sequencesnew

When one sequence ends in a different pose from where the next one starts, the robot travels between them. In the Shows tab, Between sets how that move looks: a top speed in °/s, a shortest time in seconds, or both. Leave them empty and the move uses the next sequence's own speed, as before. Two sequences that end and start on the same pose still run straight on. The time bar includes this move, so everything after it moves along to match.

Music for a whole shownew

A show can have its own Music: a track on the robot's card, with a volume and a repeat tick. It starts on the show's first pose — the robot walks to that pose first, then the music and the moves start together — and stops when the show ends or you press Stop. While a show has its own track, the music saved inside its sequences is left out, so nothing cuts the show's track off. Choose no music to keep each sequence's own music. ＋ From PC puts a track from your computer onto the robot's card and makes it the show's music in one step. Over the cable a file travels in small pieces, so a whole song takes a long time. While it is sent, a wheel shows how many percent have arrived and about how long is left, and nothing else can be done; Cancel sending stops it and takes the half-sent file back off the card. The robot's card only takes English letters, numbers, space, dot, _ and - in a track name, so a Thai name is renamed (to track- and the date if nothing is left) and Studio tells you the new name. The faster ways are the robot's WiFi or copying the song onto the SD card's /music folder. If the hub was restarted you must log in again first, and Studio now says so instead of Failed to fetch.

Music stops says how long the track plays: with the last move, a number of seconds after the show ends, or a number of seconds in all from the show's first pose — which can be before the moves end. Stop always silences it at once. A looping show never ends, so its track plays until Stop.

A sequence faster or slower in one shownew

Each sequence in a show has a speed in percent: 100 plays it as saved, 50 at half speed, 200 twice as fast. It changes that show only, never the sequence file. Pauses keep their length, and no move goes faster than the robot allows, so a very high number may not shorten every move. The time bar follows the new speed.

See a whole show on the time barnew

Open a show, or press ⇣ Show on the time bar, and every sequence of it lands on the one timeline, end to end, with a line and a name where each one begins — a repeated pass says which pass it is (wave ×2). You can then scrub through the whole show, preview it and see exactly where the hand-overs are.

The steps come from the hub, not from Studio re-reading the files: it is the same list the robot will run, so the editor cannot show a show the robot does not perform. If the time bar is holding unsaved keyframes, opening a show leaves them alone and says so — press the button when you really mean to replace them.

Moves from a video of a personnew

Sequence tab ▸ Moves from a video. Pick a video of one person, press ▶ Make moves, and Studio follows their arms frame by frame and makes moves that copy them as closely as the robot's joints allow. The found skeleton is drawn over the video, and the 3D robot can play the result at once. Then Use as new moves (replaces the time bar, asking first if it has unsaved changes) or Add after the last move. They are ordinary moves: edit any of them, then Save or Save to robot.

How close. The person's upper arm and forearm directions are put on the robot's own arm lengths, and the same solver as the drag handles places the elbow and the hand there. A shape past a joint limit lands on the nearest one the robot can make. Only the arms (and, if asked, the waist) are copied; the robot has no legs or head to follow.

Follow picks how many moves: every move eases to a stop, as on the robot, so Close follows the video more tightly but stops and starts more, and Smooth keeps only the turning points. The moves keep the video's own timing; a move faster than the servos and the peak speed limit allow is slowed to what they can do, and Studio says how much longer the whole thing became.

Move like a mirror: the robot's left copies the person's right, as a reflection does. More choices: palm or back of each hand on top (as below; "as in the video" keeps the person's elbow), turning the waist when the person turns, and which part of the video to use. A nearly straight arm cannot roll its hand, so where the asked-for side could not be shown Studio says in how many moves. Pick palm on top, always (or back) and the hand moves just enough to show that side, staying as close to the person's pose as the joints allow.

Stay with the music (on at first): every move ends on its own moment in the video, so a show built on the video's song stays in time. A move the robot is too slow for goes as far toward the pose as it can in that time instead of making everything after it late. The hand side you picked still holds on that part-way pose.

Choose what to keep. After Make moves, each move has a row: click its time to see that moment of the video and the robot's pose for it, then Keep, Keep, hand side forced, Use another moment… (type the second of the video whose pose should fill this move) or Leave out. Every move keeps its place in time, so leaving one out or filling it from elsewhere never shifts the rest off the beat.

The video is read in this browser and never leaves the PC. The body finder (MediaPipe Pose, from Google) is fetched from the internet the first time; the browser keeps it after that. Tested with a still photo and made-up skeletons, not yet on the real robot.

Palm or back of the hand on top, per handnew

A hand-like part sits on each forearm, and whether the audience sees its palm or its back on top changes how a move and the end pose feel. The 3D view draws each hand: skin colour is the palm, grey is the back.

Pose tab: each hand has ✋ Palm up and 🤚 Back up, and says which side is on top now. Timeline: every move has a picker per hand (L ✋ palm up / L 🤚 back up, and the same for R). It always shows what the move's pose really does; pick the other side and that arm turns round.

The hand stays where it is; only the arm's shape changes. The arm has no wrist twist, so the hand rolls by swinging the elbow round the shoulder-to-hand line. Joint limits cap that swing: with a straight arm, or near a limit, the hand can only turn part of the way, and Studio says so instead of moving the hand.

If the drawn palm is not on the same side as the real one, press Setup ▸ Rig setup ▸ ↻ Turn the drawn hand for that hand until they match. This replaces the old "front arm / back arm" picker.

The ⇄ button beside it plays the same shape on the other arm. It is a real mirror, not a swap of the numbers: the two arms are not built as exact opposites of each other, so copying the angles across put the hand 613 mm from where it belonged. Studio reflects the elbow and the hand in the body's own centre line and solves the arm to reach them.

Sliders, gizmos and inverse kinematics

A slider per joint, clamped to that joint's own limits. Drag the 🟢 wrist ball for 4-DOF whole-arm IK, or the 🟠 elbow ball for shoulder-only IK. Gimbal rings follow each joint's configured axis and tilt.

Flat plane viewsnew

Front, Back, Left, Right, Top and Bottom are true orthographic views — parallel edges stay parallel and nothing looks bigger for being nearer, so Shift+dragging a joint in that plane matches exactly what is on screen. The iso/free view keeps perspective, where depth is the point. Switching between them never moves the camera.

A flat view now stays flat. It did not before: a plain drag orbits the camera, so taking hold of the arm quietly turned Front back into a 3D view while the button still said Front, and the plane you had chosen no longer matched what you were looking at. In a plane view the camera cannot be orbited at all — pan and zoom still work — and because nothing orbits there, dragging a hand needs no Shift held. Press 3D to turn the view loose again; there, dragging a hand still needs Shift, because a plain drag orbits.

Live XYZ readout

Joint positions in millimetres, origin at the torso centre.

Collision checking

Arms against torso, head and each other, sampled along the whole path — not just at keyframes. Offending keyframes turn red and Run/Upload are blocked until it is fixed.

Two mirrors: left↔right and front↔backnew

A puppet has two mirrors, so there are two buttons — on the Pose tab, and on every move in the timeline.

⇄ Mirror L↔R swaps the arms: the left arm takes the right's shape and the right takes the left's. ⇅ Mirror front↔back does not swap them — each arm stays on its own side and only its reach turns round, so a gesture aimed at the audience now points behind. The waist turns to the other side either way; the shrug is unchanged.

Both are taken in the body's own frame, so a turned waist cannot tilt the mirror.

Mirror and neutral

Jump to the neutral pose, or save the current pose as the neutral. Mirror is a real reflection, not a swap of the joint numbers: the two arms are not built as exact opposites of each other, so copying the angles across put the hand 613 mm from where it belonged. Studio reflects the elbow and the hand in the body's centre line and solves each arm to reach them; the waist turns to the other side and the shrug is unchanged.

Timeline

Keyframes with time and hold

Each keyframe carries its move duration and a hold. Times auto-calculate from show speed and are floored per joint by the slowest servo in that move — the same formula the firmware uses. Any keyframe's time can also be typed in directly, which is how you make one move slower than the rest.

A time you typed is keptnew

Type a time on a move and it is pinned (📌). Editing that move's pose, editing the move before it, or changing Show speed will not re-time it any more. Before this, every small correction to a pose ran the automatic timer over the number you had chosen, and you had to type it again — every time.

The only thing that may change a pinned time is the servos' own minimum, and it can only make it longer — a move the arm cannot make in that time is not a choice anybody can make.

Times that come from a saved sequence file are not pinned, so re-opening a sequence and changing Show speed still re-times the whole thing, as it always has. A pin is for a time you typed or pinned yourself. To hold one that came from a file, press its 📌 once.

Two ways to hand the timing back to Studio: press the 📌 on that move's time box, or type a °/s for it — asking for a speed is asking to be timed. A move Studio is timing shows a 🕘 instead.

Speed per sequence, and per movenew

Show speed (°/s) is saved into the sequence file as its first step and restored when you re-edit it, so each sequence keeps its own pace. Change it and every keyframe time is recalculated.

Each keyframe also has its own °/s box — leave it blank to run at the sequence's speed, or set it to make that one gesture slower or snappier. The file sets that speed before the move and puts the sequence speed back after, so the rest of the show is untouched. Speed and time are two views of the same thing: set a speed and the time follows, type a time and the override is dropped.

Because each file sets its own speed at the start, a chain hands over cleanly — a fast sequence following a slow one runs at its own speed instead of inheriting the previous one's.

Peak speed limit is a separate safety cap on the fastest instant of a move. The robot may make a move longer than Show speed requests. Studio shows the active limit after Connect. Save to robot stores a new limit for the next restart; the current limit stays active until then. If boards are linked, set the same limit on both before synchronized playback. Raising the limit can cause harder impacts. Do not raise it while a joint loses torque.

Why a faster °/s sometimes changes nothing, and how to see it. A move eases in and out, so its fastest instant is about 1.6× its average — which means the peak limit starts deciding the time at roughly two thirds of itself. At the shipped 60 °/s that is about 38 °/s: above it, raising Show speed or a move's own °/s produced exactly the same time, silently. The arithmetic was right; it just never said so. Now every move's line names the limit that is holding it — the peak limit, or a particular joint's servo top speed — and says what to change. The ⚑ beside a move's minimum means that move is already as short as it is allowed to be.

Show speed lives inside the saved limit. The box will not accept a number above the flat point, because above it nothing gets faster — so raising the Peak speed limit and pressing Save to robot is what lets Show speed go higher. Measured on a real nong (board 67): at a saved limit of 120 the ceiling is 76 °/s; saved at 190 it is 121 °/s, and the same moves went from 130/196/327 ms to 82/124/206 ms — about a third quicker. A saved limit takes effect when the board restarts.

The Peak speed limit box is also editable with no robot connected. It is then simply the number Studio plans with, and it is saved with the project, so you can time a show away from the bench. Save to robot still needs a connection — Studio planning faster than the robot allows would be a show it cannot perform.

Suspend a keyframe instead of deleting itnew

The ● button on a keyframe chip suspends it: it stays in the timeline to edit, but is skipped when playing, exporting and uploading — so you can try the sequence without one move while you check something else, then switch it back on.

Skipping keyframe 2 of 1–2–3 creates a new, longer move 1→3. Its time is recomputed at the speed that applies — keyframe 3's own °/s if it has one, otherwise the sequence speed — so the arm covers the extra distance at the pace you asked for instead of lunging. Suspending can only ever slow a move down: a time you typed yourself is kept if it is already longer.

The crash check re-tests that new path, and the suspended pose never reaches the robot or the exported file.

Play, scrub and loopfixed

Preview in 3D, or with live ticked drive the real robot: keyframe 0 first, then each segment with its exact duration. A hold is a real pause between the moves. Pause sends STOP to freeze the arm where it is, and resuming asks only for the time still left in the segment.

Every Run is kept on the robot as last.yamlnew

▶ Run on robot, on the time bar or on a show, also saves what it runs on the robot as last.yaml. The robot's own page offers it first under Play a saved show, so the last thing you ran can be played again with no hub and no computer. A show Run keeps the same file ⇪ Save to robot writes. If the copy fails, the run still starts and the notice line says so.

Turn it off in Setup ▸ This robot ▸ Keep a copy on the robot every time I press Run; then Run sends only the sequence itself, which is quicker over a slow cable.

Three ways to put moves on the robot: ⇪ Save to robot on the time bar (what is on screen), ⇪ Save to robot in Saved moves on this PC (a saved file, as it is, without opening it), and ⇪ Save to robot on the Shows tab.

This robot's settings, from Studionew

Setup ▸ This robot sets the robot's own settings: its name (its WiFi name and name.local address change with it, so connect again after), the speed when a pose has no time, and the volume. Press ⬇ Read from robot to see what it uses now; each Save to robot sets it at once and keeps it after a restart. Joint limits, gear and offsets are in Rig setup, the peak speed limit is on the Sequence tab, and Open the robot's own page has the rest (WiFi, pins, logins).

Let the robot run the show on its ownnew

A browser stops its animation clock in a hidden tab, so a sequence driven live from Studio freezes when you switch to another tab or app. Press ⇪ Save to robot then Run on robot instead: the module plays it from its own clock and you can close the browser entirely.

This used to need an SD card. Now a board without one keeps the sequence in memory (up to 8 KB, until it reboots) and plays it just the same — the editor is unchanged, the board decides where it lands.

It starts from the move you clicked. Click a pose in the timeline and the play head parks there; Run then carries on from that pose to the end. It does not travel back to the first pose first — on a robot built into a rig, that trip back is where the arm hits something. The same is true when you switch tabs part way through a show: the robot is handed the rest of it, not the whole thing from the start. A part run is saved beside the full one as <name>.part.yaml, so your saved sequence is never overwritten by running a piece of it. And the first move after a jump is given as much time as the distance really needs, however fast the timeline had it — the robot may be standing anywhere when you press Run.

Robot-side playback is also more accurate, not less: the module interpolates every move on its own 50 Hz clock, so timing does not depend on the browser or the link. Tick monitor to watch the real robot in 3D while it runs.

While playing live, Studio now holds a silent audio track and drives the clock from a timer, which keeps most browsers from throttling a background tab — best effort, and no substitute for running it on the robot for a real show.

Monitor mode — the model follows the robot

The 3D rig animates from the robot's real joint angles, and the status line shows which sequence is playing and how long the current move has left. Use it to watch a run started from the SD card.

Rig setup — calibrate the model to your robot

Per joint: zero, limits, axis, invert, tilt

Rotation axis (roll-X / pitch-Y / yaw-Z), invert, and a three-angle axis tilt. Tilt is visual only — it is never sent to the module.

Per joint: servo, gear, pulse, speed, travel, frame rate

Plus group presets (shoulders / elbows / waist / shrug / all) and a warning when the gear and joint limits together need more travel than the servo has. Send pushes limits, gear, pulse, travel and rate to the robot; read back pulls the robot's current values into the rig.

Body dimensions and your own default

Arm lengths, joint radii, shoulder width, shrug pivot height. ★ Save current as default locks your tuned rig in, so Reset returns to yours rather than the factory scale.

Appearance

Your own STL parts

Import STL exports per body part, each with its own rotation, offset, scale and colour. Part size automatically sets the rig's lengths. Texture images can be imported and assigned.

Build the body from a URDFnew

A STEP file cannot be opened in a browser at all, and an STL carries no origin — which is why a part dragged in lands at the middle of the robot and has to be rotated, offset and scaled by hand until it looks right. A URDF carries exactly those missing numbers: where each part sits, which way it is turned, how big it is and which part hangs off which.

From SolidWorks, use the sw2urdf add-in (Tools ▸ Export as URDF). Import the meshes/*.STL it writes, then pick the .urdf in Setup ▸ Build it from a URDF. Studio lists every link with the body part it guessed from the name, which you can correct. Reading the file changes nothing — pressing Use this URDF is what places the parts, and it offers to set the arm lengths from the joint origins rather than overwriting measurements you made by hand. A mesh the URDF names but models/ does not hold is reported by name.

Two settings, because no two exports agree: Sizes are in (URDF is metres, Studio is millimetres) and Up is (URDF/ROS is Z-up, this editor is Y-up). If the robot arrives lying on its side, change the second; if it is a thousand times too big, change the first. The joint table for the nong is written out in docs/urdf_nong.md.

You may not need SolidWorks for the URDF itself. Every number the add-in would ask for — the joint tree, the origins, the axes, the limits — is already measured in the rig. python tools/make_urdf.py writes the whole file from it in one command, and rewrites it whenever the rig changes. Export one STL per body part, name them torso.stl, head.stl, L_upper.stl, L_fore.stl, R_upper.stl, R_fore.stl in models/, and that is the whole job.

Getting moves onto the robot

Export, upload and re-edit

Export /moves YAML with an explicit T on every step so linked boards stay in sync. Upload straight to the robot's SD card, or re-open a saved YAML — local or downloaded from the robot — and keep editing.

Many sequences on one card

The card holds as many /moves/*.yaml as fit. The Robot SD card panel lists them all with ▶ Run, ▶ Preview, ✎ Edit and delete on each, over WiFi, USB or RS485 — and the module's own website has the same list in its Sequences card. Give each one its own name in the name box at the top to keep them separate.

Play a saved sequence without editing itnew

▶ Play saved (Sequence tab, next to “Load for editing”) loads the sequence you picked and starts playing it right away, exactly as if you had loaded it and pressed Play — so it follows whichever clock applies: through the hub the show keeps running even with this page closed; over USB it plays from here.

▶ Preview on a Robot SD card row does the same for a file still only on the card, while ▶ Run hands it to the robot itself.

Chain one sequence into the nextnew

The Then run box (Sequence tab) writes next: into the file, so when it finishes the module starts that one by itself — a show built from short files that can each be run and edited on their own. The box offers the sequences already on the card.

It applies only when a sequence actually ends, so loop wins over it. Chains stop after 16 files, so a file pointing back at itself cannot run forever, and MOVE STOP ends the whole chain.

Camera modulenew

A third module type: an ESP32-CAM running the same firmware core as the lift and the humanoid — same identity, same commands, same website, same RS485 address, same update over WiFi. Build it with pio run -e mice_cam, or flash it from the hub like any other board.

Take a picture on its Control card shows one frame; the live view tick box refreshes it once a second. SNAP <name> saves a picture to /photos on its SD card. CAM reports and changes the sensor: CAM SIZE vga, CAM QUALITY 12, CAM FLASH ON (the white LED), CAM VFLIP 1 and CAM HMIRROR 1 for a camera mounted upside down or behind glass.

It can never also drive a servo. The camera and the on-board SD card use every usable pin on that board, which is exactly why it is a module type of its own. Its pins are fixed in the firmware rather than set on the Hardware pins page — they are etched onto the board, so "changing" one could only break the camera.

The live view is a stream (/api/cam.stream), not one request per picture: about 19 frames a second at 320×240, where repeated stills managed 7 and the original one-second timer managed 1. Only one person at a time can watch — the board has four connections in total, and a viewer holds one for as long as the picture is on screen. Untick live view to give it back.

The picture is HTTP (/api/cam.jpg), never a command reply: a JPEG is far too big for the one-line channels that RS485 and USB serial are. If the camera does not start, the card says so — it is almost always the ribbon cable not seated, or a 5V supply that cannot hold the current.

Update a module over WiFinew

It asks which firmware to send. The list is whatever this PC has built, with the board's current type marked and preselected — so the usual case is two clicks, and the unusual one is possible: picking a different type turns that board into another kind of module without finding a cable. When you do that the hub finishes the job, because a board flashed with a different type still has the old one in its own memory and would come back as blank: it waits for the module, sends SET TYPE, and reboots it once more.

It all happens on the Firmware screen. A module on the network appears there with ⚡ Write over WiFi — no cable, no reaching behind the set. The module's own row still has a ⚡ firmware… link, because the row is where you notice a board needs updating; it takes you to the one screen that does the writing.

A failed update cannot brick a board. The chip has two firmware slots (1.875 MB each) and the update goes into the one that is not running. If the WiFi drops, the PC walks away, or the image is bad, the board simply keeps booting the firmware it already had. Ask a board where it stands with OTA — it answers running=app0 size=1294617 target=app1 room=1966080 free=671463.

It is refused while the module is moving or playing a sequence — writing flash stalls the servo loop, and a reboot in the middle of a show is worse than an update that waits. Stop it first (or add force=1 if you mean it).

The first update still has to arrive by cable: a board running older firmware has no /api/ota to receive it. Flash it once over USB, and every update after that can be over the air.

Flash a board from the hubnew

Open Firmware. It lists every module type this PC has built, and under each one every board it could write it to — this PC's cables, boards on the WiFi, and cables on other PCs running the same hub. Pick the firmware, pick the board, confirm, and the hub writes it: no PlatformIO, no command line. Cables where nothing answered are listed too, which is exactly when you need this.

A type that has not been built is still shown, with the reason and the exact command that fixes it — so a missing lift looks like something you can do, not like something broken.

The hub owns every cable and shares it between its pages, but esptool cannot share. So for the length of the flash the hub gives that port up completely: it stops playing a show on it, closes the handle, and refuses to reopen it until esptool is finished. That is what all the old port is busy failures were.

It flashes what is on this PC: pio run -e mice_nong (or mice_lift) has to have been run at least once in code/firmware. If it has not, the page says so and names the command instead of offering a button that cannot work. The board keeps its stored id, name, WiFi and pins — those live in its own memory, not in the firmware.

If the board does not answer, hold its BOOT/IO0 button as the flash starts, and check the cable is a data cable. The message says so too.

A way back to the hub, from the board's own pagenew

Opening a module's website used to be a one-way trip. Typed straight into a phone there is no Back to press, and the hub is the only screen that shows the other modules. Now ← Hub is first in the board's head, as on every page.

It never guesses. Several PCs at a venue run this same hub and the addresses move with the network, so a link to the wrong one would land you on somebody else's control panel. Opened through the hub, the link is simply back to the hub serving the page. Opened directly, the board offers the hub that last spoke to it — every hub says who it is on each request it makes — and it names that PC in the link.

If no hub has been in touch, or the last one has been quiet for five minutes, there is no link. The board never invents an address, and it forgets one that has stopped being true.

The board's page admits when something failednew

Four things on the module's own website used to fail quietly and leave the page showing a state the board was not in. Each now says what happened:

• Changing a password signs you back in, and if that fails it says so — before, Setup opened on a dead session, with every card visible and every action behind it refused.
• A board that has never had a password chosen asks for one. If the board's answer cannot be read, it asks anyway: being prompted once too often is recoverable, and a prompt that turns itself off is not.
• Log out tells the board, and admits it if the board did not confirm — a logout that only forgets locally leaves the cookie working for whoever sits down next.
• A file list that could not be read says so instead of showing an empty dropdown, which already means nothing on this card.

Addresses and ports are hidden until you asknew

An IP address tells you nothing while everything is working, and it was on every row in the same grey as the name. Settings → Show technical details brings back the addresses, the cable ports and the signal strengths, and the choice is remembered in that browser.

Always shown, switch or no switch: the name, the type and the module number. The number is not trivia — it is how a module is addressed on the RS485 bus, and how two identical arms on a shelf are told apart.

It is one rule in the shared stylesheet (.tech), so a new screen marks a detail as technical and it follows the same switch — nothing to wire up and nothing to remember.

The same switch is now on every screen: this help page, the RGB wall page, the camera page, Nong Studio (typed addresses hide; Find modules still works with no typing) and each module's own website, always last in the page's head. One choice, remembered everywhere.

One board is one row, however it is reachednew

A module plugged into this PC and on the WiFi used to appear twice, as two robots. The two rows were not even equivalent: one drove it down the cable and the other over the air, so which copy you happened to click decided how the arm moved. Now it is one row, and it says every way the board can be reached — reachable on COM9 and over WiFi.

The hub matches boards on the chip: the ESP32's own MAC, which the board now reports in INFO and /api/status. It is the only identifier on a board that nobody can change — the id is a byte someone sets, the name is typed, the type is chosen.

That matters in the direction people do not expect. Two different boards out of the same box share a default id, and merging on the id would show them as one robot — a command meant for one arm going to the other. So without a chip (older firmware) the id is used only together with the type, and a board that reports a chip is never merged with one that does not.

Open the hub on a phone: a QR, and a namenew

Network shows a QR of this hub's address. Point a phone camera at it and the phone opens the hub — no number read across a room, no 192.168.137.1 typed as 192.168.13.71. The address is printed beside it for anyone working over a remote desktop.

The QR is drawn by the hub itself, with nothing installed: the encoder is part of the program. It is redrawn every time you open Network, because a laptop that moves between a venue WiFi and its own hotspot gets a new address, and a QR of the old one sends the phone nowhere.

There is a name as well: http://mice.local:8642/, answered by the hub over multicast DNS, which phones, Macs and Windows already speak. A name does not change when the address does.

Both exist because either can fail. Many venue networks block multicast between clients, and then no name resolves — the QR still works. If another program on this PC already holds the mDNS port, the page says so plainly and shows only the address, rather than printing a name that answers to nothing.

Flash from a PC that never built the firmwarenew

At a venue there is usually one laptop with PlatformIO on it and several without — and the board is plugged into whichever machine was nearest. So the image travels, not the command: Firmware lists boards on other PCs' cables as ⚡ Write over the cable on that PC. This PC sends the firmware there, and that PC writes it over its own cable. esptool only ever runs on the machine holding the board.

That PC has its own accounts, so the confirm asks for a login on it. It is used for the one request and not stored: no hub ever holds another hub's password.

Progress comes back from the machine doing the work, through this hub, because a browser cannot ask another hub directly. When the write finishes, a board that is becoming a different type is named along with the one command that finishes the job there — this PC has no route to a board on someone else's cable.

Two hubs, one rignew

Two PCs on the same WiFi can link: one shows a short code, you type it into the other, and from then on each hub lists the other's modules in its own Modules tab. Open one of them and it works exactly like a board on this PC's own cable — drive it, run sequences, watch it. The link is by address, so it survives a module moving between the two PCs.

Report a problemnew

Every hub page carries a Report button. It saves what went wrong — which page, what was happening — into a reports folder next to the program, and the hub keeps a complaints screen where each report can be marked fixed or not-a-problem. A complaint written in another language is translated into English automatically about a minute later, so the whole list reads in one language. Nothing is sent to the internet: reports stay on this PC.

The hub keeps the show runningnew

Press Play and the hub — the Python program, not the page — sends the moves. Switch tabs, minimise the window, open something else: the rehearsal keeps going, because nothing throttles a native process. The page is only the picture.

Only one thing drives the robotnew

The module plays a sequence on its own clock, and Nong Studio can send poses down the same cable at the same time. Both drove the same servos: the moves overlapped, the arm fought itself, and Pause in Studio stopped only the browser while the module carried on.

Now any command that moves the robot — POSE, JOINT, HOME, STOP, RELAX, ATTACH (and UP/DOWN/GOTO on a lift) — stops the sequence the module was playing, and the reply says (sequence stopped) so nothing loses track. Whoever moved the robot last owns it.

Settings do not interrupt a show: SPEED, LIMIT, SERVO, RANGE and every question keep it running, so you can tune a sequence while it plays. When Studio connects to a module that is already playing, it now says so instead of leaving you to guess.

Open the module's config from the editornew

⚙ Open module config in the Robot link card opens the connected board's own website in a new tab — hardware pins, WiFi, users, servo type, SD files. It follows the same link your commands take, carrying the RS485 bus id when there is one, so it always configures the board you are actually posing.

Over shared USB the module site and the editor stay open together on the one cable. In direct Web Serial mode the browser owns the port exclusively, so the button says to switch to shared USB instead.
