Command language

One text protocol on every channel. Everything the web UIs do, a script can do too.

Every module type
CommandDoes
PINGAnswers id, name and type — safe to broadcast, used for discovery
HELP / HELP <cmd>Bare HELP lists every command this board understands on one line; HELP POSE explains one. Generated from a single declaration, so it can never advertise a command it lacks — and a board of a different type correctly answers “no such command here”
INFOOne-line status JSON
SET ID | NAME | TYPE | WIFIIdentity, module type and radio mode
CFGRead or write stored settings; CFG CLEAR resets them
PIN? | PIN VALID | PIN | PIN CLEARRead, validate, set and reset the hardware pin map
FILES | FBEGIN | FDATA | FEND | FREAD | FDELSD file access over the text channel
MOVE | MOVE STOPRun or stop a YAML sequence from the card. Stopping it also stops any sound the sequence started
AUTH | USER LIST|ADD|DEL|PASSSetup-page accounts, stored on the board
REBOOTRestarts about a second later
FWBEGIN | FWDATA | FWEND | FWABORT | FWSTATNew firmware over any channel, including RS485. The other two ways both need something a bus does not have: esptool reaches the ESP32's boot loader by pulling EN and IO0 with the cable's DTR and RTS lines, and POST /api/ota talks to the board's own web server. A two-wire bus has neither, so instead the board writes its own spare slot from ordinary commands and the link underneath stops mattering. Each chunk carries its number and its length — a line cut short is still valid base64, so without the length a short chunk decodes silently and the image ends up wrong. Out-of-order and short chunks are both refused without advancing, so the sender just repeats one. The image is checked against its md5 at FWEND, while the board is still running firmware that works, and only a good one causes the reboot; FWABORT leaves it on what it had. It is slow — minutes, not seconds — which is the price of having no reset line. Started for you by the hub's Firmware tab
PERF?Is the board keeping up? How long its main loop takes, the widest gap between two servo updates while moving (20 ms is on time), what held it up longest, free memory, and how many times it has restarted since it was switched on, with the reason for the last one. CRASH, WATCHDOG or BROWNOUT there means something is wrong. Each ask starts a fresh count. python tools/bench_perf.py <port or address> runs every task on a real board and reads this around each one
Lift only
CommandDoes
UP | DOWN | STOP | HOMETravel to a limit, stop, or home and zero the encoder. STOP also silences the speaker
GOTO | STAGE?Go to a stage; report the current one
SPEED | SPEED?Raw PWM, or real units with MS / MMS
TIME?Estimated time for one stage, or to a given stage
RGB | RGB BRIGHT | RGB EFFECTColour, brightness and effects
PLAY | PLAY STOP | VOLAudio from the SD card
AMP | AMP VALID | AMP?Which amplifier is wired to this board. Normally chosen by name under Setup → Hardware pins; the board remembers it and uses it after the next restart
Nong only
CommandDoes
POSE | POSE?Move all 10 joints, optionally over T ms; read the current pose
JOINTMove one joint, by number or name
HOME | ZEROReturn to the neutral pose
STOPFreeze mid-move — the pose holds, the speaker goes quiet, and a linked partner board stops too
RELAX | ATTACHGo limp to pose by hand; power up again holding position
SPEED | SPEED? | TIME?Default speed in °/s, and move-time estimates
PACE MUSIC [°/s] | PACE NORMAL | PACE?While a show follows its song: the speed cap becomes the given °/s, or the saved music_dps (0 = the servos' top speed). Ends with the show, STOP, or a restart
SETZEROMake the current pose home — the arm does not move
LIMIT | LIMIT?Per-joint joint travel; the JSON reply carries the whole calibration
GEAR | PULSE | RANGE | RATEPer-joint reduction, pulse range, servo travel and frame rate
JCFGOne joint's whole setup in a single line — what GEAR+PULSE+RANGE+RATE+LIMIT do in five. Send rig uses it: 10 commands instead of 50, about 1.6 s down to 0.3 s
SERVOApply a servo preset to one joint or all
PLAY | PLAY STOP | VOL | AMPThe same speaker the lift has. A nong ships set to a MAX98357A on pins 12, 0 and 2 — the only three left once ten servos, the card and the bus have theirs
Camera only
CommandDoes
SNAPTake a picture; with a name it is saved to /photos on the card
CAMWhat the sensor is set to, and change it: SIZE, QUALITY, FLASH ON|OFF, VFLIP, HMIRROR
Dummy only (the hand-posed copy of the nong)
CommandDoes
POSE?The 10 joint angles the dummy is held in, same order and format as the robot; - = no pot on that joint
POT?The raw pot readings, 0-4095; -1 = no pot
DCAL | DCAL?One joint's pot calibration: CH (mux channel), ZERO (reading at 90°), SPAN (pot travel), DIR, MIN, MAX; CLEAR for defaults; DCAL? reads it all
DZEROHold the dummy in a known pose (default 90°) and each joint works out its own zero
DMUX | DMUX?Which pins the 16-channel analog switch (CD74HC4067) is on, or OFF for one ADC pin per joint
Prize dispenser only (gachapon)
CommandDoes
GDISPENSETurn until one prize falls; refused when the event is closed or the balls ran out. FORCE = the admin's extra, still counted; a name after it is kept with the record
GSPINTest turn: n pockets (n magnets with MAG), negative turns back; not counted as a prize
GHOMETurn until a magnet is over the sensor, so a pocket sits at the loading place
GSTOCKBalls in the machine: how many now, ADD more, or OFF to stop counting
GEVENTThe event: NAME, OPEN, CLOSE, or RESET its counts
GITEMWhich kind of prize this machine holds; the hub sends "give kind X" to a machine that has it
GCFG | GCFG? | G?Pockets, magnets, pockets until it falls, speed, direction, stuck time; G? reads everything
GCOUNTRESET the lifetime magnet and prize counts
