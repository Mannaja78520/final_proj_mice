Find your way around

Every page has the same head. ← Hub is always first and takes you back to Home; Show technical details is always last and brings back addresses, ports and error codes on every page at once. In between: the page's name, a line saying what it is doing, and its own buttons.

Home has one row of tabs: Home, Tools, Modules, Firmware, Network, Settings and Complaints. STOP, Report, Shortcuts and Help sit in the head, so they are there on every tab. The tools and the module list work with nobody signed in; there is one place to sign in, and a card that needs it points there instead of showing a second login box.

A module's own page (and the light strip page) has the same head, with what the board is doing in words. Reading it needs no login; anything that moves the robot asks you to sign in and says so.

In Studio, the name of your moves and the one Save are in the head. Start with the sliders, then add poses to the timeline. Your saved moves are in the Sequence tab under Open saved YAML…. On a phone, Views opens the Top / Front / 3D buttons so they do not cover the robot.

The app pages (Cameras, Voice, Reconize, Photobooth, All-Jao) ask the hub whether their program is running, so they say the right thing on a phone too.

Mice opens in the Reconize look. For a dark hall, choose Midnight in the hub’s Settings.

Finds modules on its own

Parallel scan of the whole local subnet, plus every COM port on the PC. Bluetooth phantom ports are recognised from the device type and skipped instead of being probed — they hang for ~40 s if opened.

Streaming USB probe

One request per port, so each slot fills the moment that port answers and fast ports never wait for slow ones. Identifies the module plugged in directly and every module on the RS485 bus behind it.

One cable, many pagesfixed

The hub owns each COM port and shares it, so the module website and Nong Studio can drive one cable at the same time instead of colliding with "serial already in use". Commands are atomic on the wire, so replies never interleave.

Recovers from a replugged boardfixed

After a board is unplugged or reset, Windows leaves the handle looking open and every write fails. The hub detects the stale handle, drops it and reopens — no restart.

Serves the module site over any transport

/mod?dev=wifi:<ip> or usb:<port>[:<id>]. A unified device API routes commands, status, file listing, upload, download and delete to HTTP or serial as needed.

Hosts Nong Studio

Studio lives at /studio/, with "Studio + monitor" opening it already connected to a discovered nong. Also serves the RGB page and the pinout reference.

Adding a tool costs one foldernew

Every web app is a folder in code/apps/ with an app.json naming it. The hub lists it on the main page and serves it at /app/<name>/ — no route to add, no button to hand-write. Nong Studio and this help page are registry entries pointing at where they already live, so no link changed.

The manifests are JSON that allows // comments and trailing commas, so they are comfortable to edit by hand.

Sending the rig is 5x fewer commandsnew

Send rig to robot used to push five commands per joint — fifty round trips, about 1.6 s. The new JCFG command carries a joint's whole setup in one line, so it is ten. Only joints that actually differ are sent at all, and a board older than JCFG automatically gets the individual commands instead.

The board says what it can donew

Each module reports its capabilities in its status — motion, rgb, audio, joints, servos, sd, rs485 and so on — and the module website shows each card by capability rather than by module type. A new module type therefore shows the right controls without the site being taught about it. A board running older firmware sends no capabilities and still renders correctly.

Commands declared oncenew

firmware/config/commands.json declares every command — which module type it belongs to, its arguments and a one-line explanation. The board compiles it into a table for its own HELP, and QC checks it both ways: a declared command must have a handler, and a handler must be declared. It found two commands (PINS, PINS?) that had existed undocumented.

One servo table, shared by everythingnew

firmware/config/servos.json describes every servo preset once. The firmware compiles it into a header at build time — the chip parses nothing and pays nothing — and Nong Studio fetches the same file for its dropdown. They used to be two hand-kept copies that could drift apart with nothing to notice; QC now fails if they ever disagree.

Reachable from other devices

Binds all interfaces, so phones and laptops on the same WiFi can open the hub and every module page through it.

This help page, offlinenew

Served from the PC at /help — no internet, no account. Linked from Tools on the hub's main page, and searchable with the filter at the top.

Works on any screennew

The hub, the module website, Nong Studio and this page all lay out for phones, tablets and large monitors, with bigger touch targets on a touchscreen. Studio stacks the 3D view above its panel below 860px instead of squeezing both, and on a phone its view buttons (Top, Front, 3D…) fold behind one Views ▾ button.

Rebuilding or stopping MiceHubnew

To rebuild the single-file executable from source: python -m PyInstaller --clean MiceHub.spec

If MiceHub.exe is running, the build automatically terminates it to avoid PermissionError: [WinError 5] Access is denied. You can also stop running instances manually with: taskkill /F /IM MiceHub.exe (or python main.py --kill).

Module website

One site per module, identical over every transport. The hub serves the board's own HTML with a transport shim, so a board with no WiFi shows the same page over a cable.

Three tabs, not one long pagenew

Control (the module's own controls), Sequences & files (run a sequence, the SD card, the console) and Setup (login, settings, pins, calibration). Thirteen cards in one column meant scrolling past the arm controls to reach the SD card.

The Setup cards still stay hidden until you log in — one rule decides both which tab a card is on and whether you may see it, so the two can never disagree.

Controls match the real board

Control cards render from the board's actual type — a nong board shows only nong controls, a lift only lift. No login needed to drive the robot.

📍 แท็บ 1: Pose — ปรับแต่งท่าทาง เซอร์โว 10 จุด และทิศทางมือ

ใช้สำหรับจัดท่าทางของหุ่นยนต์ Humanoid ท่อนบน โดยมีเซอร์โวควบคุม 10 ข้อต่อหลัก:

  • L/R shoulder pitch & roll: ข้อต่อไหล่แบบ Universal Joint สองตัวขับเคลื่อนมุมก้ม-เงย และกาง-หุบ (เซอร์โว PDI-1181MG หมุนได้กว้าง 270°)
  • L/R elbow pitch & roll: ข้อต่อข้อศอกสองตัวขับเคลื่อนการงอแขนและการหมุนท่อนแขน (เซอร์โว MG90S 180°)
  • Waist (เอว): เซอร์โว TianKongRC 35kg พลังแรงบิดสูง หมุนเอวซ้าย-ขวา 270°
  • Shrug (ยักไหล่): กลไก 4-bar linkage ยกสะบักไหล่ทั้งสองข้างขึ้นพร้อมกัน (~6°)
  • Hand Orientation: เลือกระหว่าง L/R on edge (สันมือตั้ง), palm down (คว่ำมือ), palm up (หงายมือ) เพื่อล็อกแนวหมุนของข้อมือให้สวยงามตามธรรมชาติ

⏱️ แท็บ 2: Sequence — การคำนวณเวลา ความเร็วปลอดภัย และจัดการ SD Card

ควบคุมพฤติกรรมการเล่นท่าทางตามหลักฟิสิกส์จริงของฮาร์ดแวร์:

  • สูตรคำนวณเวลาอัตโนมัติ: Time = Biggest Joint Change ÷ Servo Speed (°/s) ระบบจะหาข้อต่อที่ต้องหมุนไกลที่สุด และคำนวณเวลาให้พอดีกับความเร็วสูงสุดที่ตั้งไว้
  • Safe Speed Cap (ความเร็วสูงสุดปลอดภัย): ค่าเริ่มต้นจำกัดที่ 375–400°/s เพื่อป้องกันไม่ให้เซอร์โวกระชากตัวหุ่นยนต์จนโครงสร้างปริแตก
  • Robot SD Card File Manager: ดูรายการไฟล์ YAML ทั้งหมดที่อยู่ในการ์ด SD ของบอร์ด ESP32 สามารถกด Upload, Download กลับมาแก้ หรือ Delete ทิ้งได้โดยตรง

🔌 แท็บ 5: Robot — จัดการการเชื่อมต่อฮาร์ดแวร์จริง และ Zero Calibration

Several people can watch at once

The board itself can only be read by one thing at a time, and that is the hardware rather than a limit anybody chose: it has a single frame buffer, and taking a frame reclaims the one already on loan, so two streams would tear each other's pictures. The hub therefore holds one connection to each camera and feeds every viewer from it. Open this page on as many screens as you like.

A slow viewer — a phone on poor WiFi — is given the newest frame each time it is ready for another, so it drops frames rather than holding anyone else back. If a camera stops answering, the live view says so instead of leaving an old picture on screen pretending to be now.

A camera has to be on WiFi to be seen

Pictures do not travel down a USB or RS485 cable: those carry one line of text at a time, and a JPEG is not that. A camera reachable only on a cable is listed, and says so, with its picture controls switched off. Its settings still work over the cable.

Settings

Every setting the sensor has — brightness, contrast, saturation, white balance, exposure, gain, effects and the correction switches — lives on the module's own page under Settings, grouped, with one control to put everything back to default. The list is built from what the board reports, so it is always what that board can really do.

Two things it will tell you rather than hide. A setting this sensor does not have is shown greyed with this sensor does not have it — the OV2640 has no sharpness, for instance. And a setting that only applies while another is off (exposure time needs auto exposure off, gain needs auto gain off) says which one to turn off.

There is no autofocus. The OV2640 on these boards is fixed focus, so there is nothing to switch on and no control for it.

Ask the rig a question

The Voice app in the Tools list: type a question, the rig answers. The answers come from a helper program that runs on this PC next to the hub (the hub itself never carries an AI — it only passes the question along and the answer back).

Speak instead of typingnew

The Voice page has a Press to talk button: press it, speak, press again to stop, and your words appear in the box ready to send. The listening runs on this PC too. Which languages it hears — and the words each language gets wrong often — live in config/voice.json; adding a language is one entry there.

The rig speaks one thing at a timenew

Everything the rig says goes through one queue on the hub: a greeting, an answer from this page spoken through a robot, a message from another program on this PC. So two of them never talk over each other. Something that arrives while the rig is talking either waits its turn or is skipped — whoever asked chooses — and a greeting that waited too long is dropped, because the person has walked on (maxAgeSeconds, 30 seconds unless changed).

Where it speaks. Speakers are found by themselves: every robot with a speaker that the hub reaches over WiFi, and this PC's own speakers. A robot reached only by cable is listed with that reason, and a robot whose board has no amplifier wired says so after its first try — plug one in and it is asked again. Which one is the default, and which voice each uses, is config/speakers.json; the hub writes it when somebody picks on a screen.

Live sound wins. Somebody sending sound to a robot (Send sound to the robot on its page) takes the speaker; greetings wait until it has been quiet for two seconds. If the rig's own speech takes a speaker back, the sending page stops and says so instead of sending into nothing.

Stop All silences it all — what is being said, everything waiting, and live sound — with no login, like every other stop.

In conversation mode this page waits for the robot to finish before it listens again, and throws away anything it heard while the robot was talking, so it never answers its own voice.

For a program on this PC: POST /api/speak with JSON {text, to, voice, lang, whenBusy: "queue"|"skip", take, move, module, maxAgeSeconds} needs no login when it comes from this PC with Content-Type: application/json and no browser headers; from the network, or from a web page, it needs one. GET /api/speak shows what is said and what waits (login), GET /api/speakers lists the speakers, POST /api/speak/stop is quiet now. The voice helper itself answers programs only: a web page, or any address that is not an IP or localhost, is refused.

It can greet you by namenew

Beside the answer box there is a face badge and two buttons. Check who I am uses the camera of the device the page is open on: it takes one picture, asks the face app who it is, and shows the name. The picture is not kept — nothing is written to the face app's history and no image lands on the disk. The name is remembered for two minutes, so the next answers greet that person by name in Thai, English, Japanese or Chinese.

That promise has to come from the face app itself. Before sending anything the page asks the face app whether it can look without keeping; a face app that cannot (the current Reconize cannot) is sent no picture at all, and the line under the camera says so and the looking stops. Recognition then still works through a camera the face app watches, or through Open Reconize. When the face app learns to look without keeping, this button works again by itself.

Next to it, Check by itself keeps looking every few seconds, so nobody has to press anything — still keeping no pictures. It stops while the tab is hidden, and it lets the camera go the moment it is switched off. How often it looks is face.autoSeconds in config/voice.json.

The list beside the switch holds two kinds of camera. Cameras the face app watches are the stations it already runs — its kiosk, a CCTV camera, a phone, or a PC watching several cameras at once. Picking one of those opens no camera here: the face app is already looking through that lens, and Voice simply reads what it sees. That is how one camera serves both programs at the same time. Under This device are the cameras of the machine the page is open on, for when no station is running.

It starts on the camera the face app saved as its own default, so choosing there chooses here too; picking another is remembered in this browser only, the same way the face app's kiosk remembers its own.

How fast a name shows. Names come from the face app's live camera through the rig's face watcher, so a face shows here about as fast as the face app sees it. When the watcher is not running, the page starts it by itself (only the watcher, never the face app); until then names come from the face app's history, which is slow.

👤 Use faces at the start of that row turns face recognition off altogether: no camera, no names, nothing waited on, and every answer comes the plain way. Tick it again to bring faces back. It is saved for the rig, not only this browser.

Show the camera keeps a live picture of the chosen camera under the row. This device's camera is shown only here; a camera on the rig comes through the hub, the same picture the face watcher reads. That way keeps a record of every sighting, which is what an event needs; the button above is for a quick hello. Where the face app lives is one entry in config/partners.json — a second face app is an entry there, not new code.

Saved answers firstnew

A question close to a saved one is answered instantly from apps/voice/qa_data.json — the same trick as the original prototype, and the part that works with no AI at all. Add or change an answer by editing that file; the helper reads it fresh every time, so there is nothing to restart.

If a question is only somewhat close to a saved one, the rig does not guess — it asks the visitor to say it again. A confident wrong answer is worse than asking twice.

A saved answer can also carry a move: give the entry a move (a saved sequence file) and a module (which robot plays it — its name as the modules screen shows it), and the robot performs that sequence when the answer is given. The name is looked up at play time, so the robot can be plugged into any PC without editing anything; if no robot of that name is connected, the page says so plainly. While that robot is already moving, another ask is answered in words — it never queues and never cuts the running move. A Stop the move button stays beside it until the sequence ends.

Ask for a language, a reading or a new poemnew

Say "Please answer in English" (or ตอบเป็นภาษาไทย, 英語で答えて, 用中文回答) anywhere in the question, and the answer comes in that language, even when the rest of the question is in another one.

Say "Read this aloud: …" (or ช่วยอ่าน: …, 読んでください：…, 请朗读：…) and the rig reads exactly those words, with nothing added.

Ask it to write a new poem (แต่งกลอนใหม่ …, "write a poem about …") and it makes up a new one instead of reciting the saved poem. If the answer does not look like a poem (a list, a greeting, too few lines, the old poem), it says sorry honestly instead. The small model on this PC usually cannot write a good Thai poem yet; pick a stronger service for Writing verse on the Voice page once you have its key. The shape of the poem is checked, its rhyme and rhythm are not.

English words spoken inside Thai, like parking or restroom, still find their saved answers when the listener writes them in Thai letters. When a Thai greeting is followed by an English question, the rig listens to it a second time in English, but only if that part really sounds English, so a Thai question is never answered in English. Rules, phrases and loanwords are data in config/voice_intents.json (replyLanguage, readAloud, compose, loanwords, codeSwitch); the second hearing adds one listening pass only when no saved answer fits.

One brain, many PCsnew

The answering helper normally listens to this PC only. To make one PC the brain for every hub at the venue, write that PC's address in service in config/voice.json there (instead of 127.0.0.1) and point every other hub's own config/voice.json at it. Sharing is opt-in by editing, never automatic — and the tradeoff is written next to the setting: the helper itself has no password, so anything on the venue WiFi could then ask it or make it speak. Moving a robot stays safe: that still needs a login at whichever hub you use.

Out loudnew

The rig can also speak its answer. Turn on 🔊 Sound here on the Voice page to hear it in the browser too; the choice is remembered. Saved answers are prepared ahead of time, so they sound instantly. When the online voice cannot be reached, this PC's own voice stands in for that line only, and the good voice is used again as soon as it answers. While it stands in, a yellow line under the status says so and why (for example: the natural voice is not installed on this PC, or the PC is offline).

Speaking manner: polite, friendly, playful, sweet, sassy, poem recitalnew

On the Voice page, Speaking manner picks how the rig says its lines; ▶ Try plays a sample first. "As now" keeps today's voice. An event (scenario) can have its own manner. The words of a line are never changed.

Sassy (ฟาดๆ แบบเจ๊) is a cheeky big-sister manner: a sharper voice, and new answers from the AI call the robot เจ๊ and end with ค่ะ, teasing a little but never rude to a visitor. Saved answers keep their words; only their ending (ครับ to ค่ะ) and the robot's word for itself follow the manner. The small AI on this PC follows the ending reliably, the sassy wording only sometimes.

Thai voice with feeling (this PC) says Thai lines with a real feeling: friendly and playful sound happy, polite is calm, sweet uses a soft sad tone (the nearest it knows), all in the robot's own voice. It runs on this PC's graphics card with no internet and no key, is tried first while a manner is on, and starts by itself (about 20 seconds after the helper starts; until then the usual voice speaks). It makes a 5-second line in about 3 seconds, then saved answers play at once. It speaks Thai only; English lines go to the usual voice. Its model may not be used commercially. Install once: python apps/voice/tts_spark/setup.py (3.8 GB, into .local/tts_spark, not in git); it listens on 127.0.0.1:8779. Words were checked by hearing them back (0.87-1.0 alike); whether the feeling is right needs a human ear.

What a manner really does depends on the speaking service, and the page says which: a service that takes a manner in words (Google Gemini voice, with its key) changes the voice itself. The free Microsoft voices can change only speed and pitch, so they sound lighter or slower, not truly emotional, and a poem recital there is a slow reading, not a real ทำนองเสนาะ tune. This PC's own voice cannot change at all. A manner is never dropped silently: the quick device voice is not used while one is chosen. Manners are data in config/voice_styles.json; each service's ability is the speak job's styles (instruct / emotion / prosody / none) in config/voice_providers.json; /say answers X-Voice-Style with how it was applied.

Gestures while it talksnew

👋 Gestures beside 🤖 Move: an answer that has no move of its own makes the robot's arms move with the words, starting when the sound starts and lasting as long as it. The gestures are picked at random to fit the words and the speaking manner, fitted to the robot's size and kept clear of its body by Nong Studio (Sequence tab, Moves while talking), where they are changed, tried and switched off per event. Stop stops them with the answer. The robot used is the one picked under Robot, else the nong robot that answers; a show that is already playing is never interrupted.

Teach it new answersnew

The Settings under the question are tabs, one topic each:

Answers is a sheet, like a spreadsheet: one row per answer, one column per language, with the ways people ask it on top (one per line) and the reply under them. Click a cell and type — nothing moves to a form somewhere else. ＋ Add a row puts a new row on top, ▶ plays a cell, 🌐 Translate fills a row's empty languages, and a language left empty is translated when you save. Changed rows are marked; Save answers keeps them all, Undo changes puts back what is saved. A robot move is a robot and one of its saved sequences, both picked from a list.

Voice — one voice that speaks every language (best: a Thai name inside an English answer is still read), or a voice per language, with ▶ Try beside each, plus speed and pitch. Listening — fast / balanced / most accurate, and the words it often mishears. Personality — what the rig is being (a scenario, which may have its own voice and speed), its polite word and what it calls itself. Faces — how long a name is remembered. The helper's address and the AI model are under Advanced, behind the Show technical details switch.

How it speaks Thainew — the small model that answers when nothing is saved used to write uneven Thai: it ended one sentence ครับ and the next ค่ะ, called itself ผม then ฉัน, stopped in the middle of a word, and now and then answered a Thai question in English. The Personality tab fixes the first two by choosing one of each and changing anything else it writes, gives Thai more room to finish a sentence (Thai costs two to four times more room than English, which is why the setting that suited English cut Thai short), and sets what the rig says when it has nothing to say.

Three things happen to every answer before it is spoken: an answer that is still unfinished is cut back to its last whole sentence, an answer in the wrong language is asked for again and then given up on, and an answer whose only Thai is the polite ending is treated as no answer at all. In every one of those cases the rig says it does not know and points at a member of staff. That is on purpose: it never invents a password, a price, a time, a floor, a place or an event. The most reliable way to improve what it says is not this tab — it is adding the answer under Answers, because a saved answer always wins.

Saving needs the same login as everything that can change the rig. A change reaches the running helper at once — nothing to restart, no file to edit by hand.

What works today

Open Reconize starts it if it is not running and shows it in the page. Is the rig following it? says whether the rig is seeing people arrive. When it is not, Start following Reconize starts Reconize and the rig's own face helper together, in one press. Under the open button a line says whether the installed Reconize is the version Mice was tested with; a newer one is only pointed out, and everything keeps working as before.

What the rig says is where you choose the words. Nothing is said until you tick Greet people the face app sees and press Save. Saving asks you to sign in on the hub page first, because it changes what a robot says to a guest. The next person who arrives already gets the new words; nothing needs restarting.

  • The words. One line for each case: somebody's first visit today, somebody who already came today, and somebody it does not know. Write {title} where the polite word goes and {name} where the name goes. Somebody it does not know is never called by a name, so only {title} works in that line, and the page refuses to save otherwise.
  • Cameras. Each camera that has seen somebody appears by itself. Pick whether it says hello, says goodbye or only counts, which speaker says it, and a saved move a robot plays with it. A camera you never set up only counts, so a new camera never starts talking on its own. Open Its own words to give one camera different words.
  • Once per person. The same person is greeted at most once in the minutes you choose, whichever camera sees them. Somebody it does not know is greeted at most once per camera in the seconds you choose.
  • If the rig is busy. skip this hello drops it while the rig is talking or playing a show; wait its turn says it afterwards. A greeting never stops a show.
  • Celebrations. Said once a day when that many people have come today, by Reconize's own count. Each can play a move too.
  • Titles. Give a particular person their own polite word, such as อาจารย์, instead of the usual one.

If it says Reconize is not answering, start it with start.bat in its own folder and wait about fifteen seconds — it loads a face model before it answers anything, so not answering and not started look the same for those first seconds.

Where Reconize lives, and how to move it

Its addresses are written in config/partners.json — one entry for each outside program Mice follows. Change the address there and the button follows on the next refresh. Nothing is compiled in, so moving Reconize to another port or another PC costs one edit and no rebuild.

That same file is how the next outside program is added: one entry, no code. Each entry says where the app is, how to log in to it, where its events come from, and — just as important — what each of those sources cannot tell us, so the rig never promises more than it can see.

No password is kept in that folder, and none ever will be. Every file belonging to a tool is served to anyone who can reach the hub, with no login at all — so a password put there would be readable by everybody on the venue WiFi. Logins for Reconize live beside the hub's own password file instead, outside anything that is served.

We never change Reconize itself

It updates itself, often, and its updater throws away anything it finds that it did not write. So Mice never puts a file in its folder, never runs its updater, and never opens its database directly — reading that database while it is running would block its own writing. Everything goes through its web address, the same way any other program would talk to it.

Only answer when somebody is there

The Voice screen can be set to take questions only while somebody stands in front of a camera (in config/voice.json, presence, off at first). If Reconize is not running, or has no camera that can tell, questions are taken as usual: a broken camera never makes the rig deaf.

All of this is tested against stand-ins for Reconize and the robot, not yet with the real cameras at the lab.

Each of those arrives as its own small change, and the plan for all of it is docs/system_integral.html, beside this project's own plan.

🎁 Prize machines — gachapon (เครื่องแจกของรางวัล / กาชาปอง)

📐 1. สถาปัตยกรรมล้อหมุน 4 ช่อง (Revolver Mechanism)

หมุนทิศทางตามเข็มนาฬิกา (CW, dir: 1)
🟢 Continuous Vending (โหมดแจกปกติ: drop: 1)

เมื่อมีแคปซูลบรรจุพร้อมทั้ง 4 ช่อง การแจกของแต่ละครั้ง หมุนเพียง 1 แม่เหล็ก (90° / 1 ช่อง) แคปซูลในช่องถัดไปจะหล่นลงรางทันที ทำงานรวดเร็ว กระชับ ไม่เสียเวลาหมุนฟรี

🔵 Initial Prime Mode (โหมดโหลดตู้ครั้งแรก: drop: 2)

ตามระยะใน CAD ระหว่างจุดรับของ (ช่อง 2) กับปากรางปล่อย (ช่อง 4) ห่างกัน 180° (2 ช่อง) ใช้เฉพาะตอนเริ่มโหลดลูกแรกเข้าตู้ว่างให้พร้อมแจก

🔄 2. วงรอบการแจกของ 4 ขั้นตอน (4-Phase Safety Settle Cycle)

ออกแบบพิเศษป้องกันของติดคาปากราง (Dual-Rocking Agitation) และดูดกลับเข้ากึ่งกลาง Hall แม่นยำ 100%

Phase 1 180 ms
⏩ Forward Overshoot

หมุนเลยปากรางปล่อยช้าๆ (ความเร็ว overshoot_speed: 380) เพื่อให้แรงโน้มถ่วงเริ่มดึงแคปซูลให้ลื่นไหลลงราง

Phase 2 250 ms
🔁 Reverse Agitation

โยกถอยหลังข้ามแม่เหล็กไปอีกฝั่ง (ความเร็ว return_speed: 360) เขย่าสะบัดให้แคปซูลที่ติดหลุดลงไป แล้วหยุดพัก 60 ms ตัดแรงเฉื่อย

Phase 3 Micro-Step
🎯 Dead-Center Alignment

ย่องก้าวสั้นๆ (15 ms ที่ center_speed: 260) เข้าหาแม่เหล็ก พอเซนเซอร์แตะขอบ จะแทงเข้า Sweet Spot 18 ms แล้วล็อกเบรกตรงกลางทันที

Phase 4 5,000 ms
⏸️ Observation Pause

หยุดนิ่งตรงกลาง 5 วินาที (ปรับลดได้ 2s/5s) เพื่อให้แอดมินหรือผู้รับของมองเห็นสถานะของหล่นชัดเจน ไฟ at_hall ขึ้นเขียวเสถียร 100%

🔑 Accounts and passwords

A new hub and every board start with two logins: super_admin and admin, both with the password admin123. These are defaults everybody knows, so change them.

Change your own password or namenew

Log in, then press My account in the login box. Type your current password and a new one (8 characters or more), or a new username. While an account still uses admin123, the login box says so on every page.

One login for the hub, Nong Studio and the robotsnew

Log in once, on the hub page or in Nong Studio, and both are logged in. When a robot on WiFi asks for its own login, the hub first tries the account you logged in with, then the logins robots ship with (listed in config/board_logins.json). A robot with none of those accounts says so, and still works over its USB or RS485 cable.

Robot home and show neutral are two different posesnew

Home is where the robot goes when it powers on and when you press Home. Set it in Nong Studio's Robot card with Keep this as robot home, in the Setup table's start° column, or on the robot's own page (⚙ Open module): jog the arm, then Keep where the arm is now as home, or type the start angles and press Save these start angles. Neutral is the rest pose of a show and stays in Studio: Keep this as neutral never changes the robot.

A frozen Studio page stops the robotnew

When the hub plays a show from Nong Studio and the Studio page freezes, the hub stops the show and the robot within a few seconds, and says why. Hiding the tab or closing Studio on purpose still lets the show carry on by itself. Studio beats POST /api/play/beat every second while on screen; a watched show silent for 4 s is stopped (ShowPlayer.BEAT_TIMEOUT).

See distances on the robot in Studionew

Press 📏 Distances under the view buttons in Nong Studio's 3D view, or hold the D key, to see dashed lines with the length in mm: each elbow to its hand, elbow to elbow, hand to hand, and on each side the shoulder to its elbow and the shoulder to its hand. They follow the pose as you move it. The pairs are listed in nong/main_python_set_nong/web/distances.json; add a pair there to measure something else.

Open one app on its ownnew

Each app (Nong Studio, Voice, Faces, Camera…) can open in its own window without going through the hub page. Double-click its shortcut in the Apps folder next to MiceHub.exe. If the hub is not running yet, the shortcut starts it too; if it is, the same hub is used, so the robot cables are still shared. Shortcut = MiceHub.exe --open <app id>. Make the shortcuts again after adding an app: python tools/make_app_shortcuts.py (add --desktop for the Desktop). The browser used for the window is listed in config/app_window.json.

A move's music list stays opennew

Press ♪ on a move to choose a track and its volume. The list now works whenever the robot is connected, with or without live, and clicking it no longer closes it before you can choose.

The Zero position lock uses your hub loginnew

In Nong Studio the Zero position card opens with the same user name and password as the hub (for example admin / admin123). The old browser-only password is gone. On the robot's own page the zero card is under Setup, after logging in.

Studio says when its joint limits differ from the robot'snew

When Studio connects it compares its joint limits with the robot's. If they differ, the arm would stop short of the preview, so Studio says which joints and offers Use the robot's limits or Send Studio's limits to the robot.

A looping show goes back to its start at the robot's pacenew

With loop on, the end of the show is followed by the move back to the first pose, timed like any other move, so the preview and the real arm stay together round after round. The hub also waits as long as the robot says a move really takes.

Delete a saved YAMLnew

Pick it in the saved list and press 🗑 Delete. It is moved to sequences/.deleted on this PC, so a mistake can be put back. To edit one, press Load for editing, change it, and 💾 Save.

A frozen Studio page reports itselfnew

If the Studio page stops for more than 1.5 seconds, it sends the hub a short report of what was running (playing, live, monitor, slow robot calls). It appears with the other reports on the hub.

A USB-RS485 adapter needs no bus id typednew

In Nong Studio pick + USB / RS485 (shared), choose the port and press Connect. If nothing answers on the cable itself, Studio asks the hub which robot is on the bus behind it and uses that one.

Identity & configuration

One binary per module typenew

A board runs one module type, so it now carries one: pio run -e mice_nong, -e mice_lift, or -e mice_blank for a board that is not a module yet.

Every board used to carry every type — a humanoid flashed the lift's motor code, its RGB strip, its MP3 support and its web cards, with only a JavaScript check keeping them off the screen. That was 74.9% of the chip's flash on every board. A nong build is now 65.5% and does not contain the lift's page at all: the wrong controls are absent, not hidden, so no script bug can show them. The room this frees is what makes flashing over WiFi (which needs two copies of the firmware on the chip) possible later.

The source stays shared. One marker says which module type a card, a command or a block of code belongs to, and the build takes only its own.

The board still confirms its type

SET TYPE lift|nong|blank + reboot, from the Settings card or any channel. A binary only accepts the types it was built with, so SET TYPE lift on a humanoid build answers ERR unknown type (nong,blank) instead of booting a module that is not there.

Runtime pin map, stored on the board

Every pin lives in the board's own NVS memory, not in the source — motor, encoder, limits, RS485, SD, I2S and all 10 servos. Set from the website or with PIN <name> <gpio>. One firmware fits any wiring.

PIN VALID classifies every GPIO (ok / strap / input-only / flash / rgb) and reports pwm+adc+dac capability, so the picker can warn before you pick a pin that cannot work. The WS2812 data pin is the one exception — FastLED fixes it at compile time.

Settings that survive without an SD card

CFG <key> <value> stores settings in NVS and overrides module.yaml: encoder leds speed speed_mms stages stage_mm mm_per_rev counts_per_rev max_rpm counts_per_stage volume speed_dps max_dps safe_dps link.

The arm never moves faster than its safety speednew

Every move of the nong, from Studio, a show or a command, is slowed so no joint passes 60°/s at its fastest point. It is measured from where the arm really is, so a jump to a far pose takes longer instead of slamming. Change it with CFG safe_dps <5-1000> and a reboot. Studio reads the robot's value when it connects and times moves the same way.

Name & bus address

SET NAME also renames the WiFi hostname, the .local address and the AP hotspot. SET ID 1–247 sets the RS485 address.

Connectivity

A bad network never stalls the robotnew

The WiFi code runs in the same loop as the servo interpolation, so anything that waits there would stop a joint mid-move — exactly when the venue's network is worst. The connect path is a polled state machine with timeouts: it tries, gives up, scans in the background, falls back to its own hotspot, and keeps retrying the real network in case it appears later. With WiFi set to OFF it does no radio work at all.

Even renaming the module defers its radio restart instead of waiting for it. QC fails if a blocking wait is ever added back.

Three WiFi modes

SET WIFI ON joins your network with hotspot fallback (default), AP always hosts its own hotspot, OFF disables the radio entirely for the fastest boot and USB/RS485-only operation.

The radio changes live — nothing needs a rebootnew

WIFI on its own answers one line saying exactly where the radio is: mode, state, which network it is trying, its IP and signal, its own hotspot name and how many modules are connected to it. WIFI ON|OFF|AP changes the mode on the spot, WIFI RETRY tries the stored network again without waiting for the 60 second clock, and WIFI SCAN lists the 2.4 GHz networks this board can actually see — which answers "why won't it join?" directly.

SET WIFI <ssid> <pass> now joins immediately too. It used to answer "reboot to apply", so correcting a mistyped network name meant power-cycling a module and leaving the arm wherever it stopped. The scan is asynchronous, so none of this can stall a joint mid-move.

The fastest way in is picked for younew

When a robot is plugged in, on the RS485 cable and on WiFi all at once, the hub times each way and sends commands down the quickest one. Measured on a nong: the RS485 cable answered in about 6 ms, WiFi in about 60 ms. ⚙ Open module and Studio + monitor keep choosing while open, so if the cable is pulled they carry on over WiFi, and if the robot drops off WiFi they go back to the cable after one command that got no answer. The Modules tab marks the way in use as fastest, in use; the timings are behind the technical switch. The settings are in config/route_latency.json.

Every module shares its WiFinew

A module in ON mode hosts its own hotspot all the time, including while it is connected to the show network. So a module parked out of router range can join a nearby module's hotspot and be reached through it, and a module you cannot reach any other way is always still there at 192.168.4.1 to be fixed. Previously the hotspot was dropped the moment the module got online, so it shared nothing.

The credentials you set on the module are always what gets tried first — the ones compiled into the firmware are only a factory fallback for a board nobody has set up yet.

A module that shares its WiFi answers a little slowerfixed

A module hosting its own hotspot and using the show network has one radio doing both, so it time-slices and occasionally answers late. Two things were quietly breaking because of it:

The hub lost modules that were online. Its network sweep waited 0.6 s per address; the lift answered that 7 times in 8, so the hub dropped it from the list on 2 scans out of 3 while it sat there working perfectly. The hub now sweeps fast to find anything new, then goes back and asks the addresses it already knows patiently. A module that has genuinely gone still disappears.

REACH failed most of the time over a shared hotspot — 1 of 6, while the far module answered the PC 6 of 6 throughout, so the far module was never at fault. It now retries within a bounded budget: 20 of 20, both directions. Over a direct module hotspot (one hop, no sharing) a single attempt was always enough.

Modules on a different subnet are found toofixed

The hub's network sweep only walks the PC's own /24, so a module on a different subnet was invisible to it however reachable it actually was. Seen on a dorm network: the PC on 10.94.163.x, both modules on 192.168.100.x, answering the PC perfectly — and the hub listed nothing at all.

The hub was plugged into both over USB the whole time, and a module's INFO carries its own IP. So plugging a module in once is now enough for the hub to find it over WiFi afterwards, whatever subnet it ended up on. Addresses already known are re-checked every scan regardless of subnet.

Name the moves in a sequencenew

The timeline showed 0 start pose and then 1, 2, 3 — which says nothing about what the show does. Each move now has a name you type straight on its chip: “wave”, “reach cup”, “bow”. The number stays, because that is what every message and warning refers to.

The name is saved with the project and written into the exported file as a comment — so every existing player still reads the file unchanged, the firmware needs no new step key, and anyone opening the YAML can see what each step was meant to be. Clearing a name removes it rather than storing an empty one.

Clicking a move previews it at that move's speedfixed

With a sequence set to 40 or 60 deg/s, clicking a move in the timeline still snapped the arm across at full speed. Two different jobs were sharing one path.

Dragging a slider should follow your hand, so the pose is sent with a time measured from the link's own round trip — deliberately quick. Clicking a move is not that: it should travel the way the move travels in the show, or what you are previewing is not what will happen. Now it carries that move's own time, taken from the played timeline, so a move after a suspended keyframe gets its re-timed value rather than the number stored against it.

QC checks the time that actually reached the module, not the editor's opinion of it — the editor's opinion was exactly what was wrong.

Save and open YAML movesnew

Type a name and press 💾 Save. There is one name and one Save: it writes NAME.yaml, the file the robot, Voice and the other apps play, and NAME.json, the project you open later to keep editing. The name box and Save are at the top of the page, and the line beside the title says whether what you see is saved. If a different file with that name is already saved, Studio asks before replacing it.

To edit a saved one, open the Sequence tab and pick it in Open saved YAML…: its moves open in the timeline straight away, and saving writes back to the same file.

Nothing is replaced without asking. If the time bar has changes that are not saved and you open another file, Studio asks: Save, then continue, Don't save, or Cancel. To stop the question, untick it in Setup ▸ Saving. A copy of unsaved moves is still kept in this browser and offered back the next time Studio opens.

Long tabs fold. In Sequence, Robot and Setup, click a card's title to hide or show it, like the extra cards in Pose. Setup opens as a short list of titles; Studio remembers which cards you left open.

The real robot's body and servos, from the STEP filenew

In Setup ▸ rig, pick use a measured body… ▸ Nong, measured from the STEP file. The sizes change at once. Studio then shows the servos and gears the STEP file says the robot has and asks before using them, because they replace your own settings. The shrug is a 4-bar linkage: its servo turns 2.38° for each 1° of shrug, and ±16° of shrug needs about ±38° of servo. Press Send Studio's limits to the robot to put them on the robot.

Technical

The numbers live in config/rig_presets.json. After the CAD changes, run python tools/step_preset.py --write: it reads the STEP assembly, finds each pin from the part's hole axes, and works out the linkage again. Gears are whole teeth (50:119) because the board keeps whole numbers: a ratio typed as 1:4.5 reached the robot as 1:4.

Make the timeline taller or shorternew

Drag the thin line above the timeline up or down. The timeline keeps that size next time and scrolls inside itself when it holds more than fits. With the line selected, the arrow keys change it too; double-click the line to put it back to its own size.

Clicking a move while the show plays is safefixed

Clicking a move during Play used to send the show back to the pose before it and replay the move — a sudden swing that can hit something or break a servo.

Now a click during Play stops the show, moves the arm from where it is to the pose you clicked at the show's speed, and then carries on with the next move. Nothing goes backwards. Jumping along the time bar also moves the arm at the show's speed, never at slider speed.

The time barnew

Under the Timeline buttons there is a time bar across the whole width. Each move is a block as wide as it is long, so a two-second move really looks twice a one-second one, and the waits between them show as their own lighter bands. The seconds are marked underneath.

Drag anywhere on it to go to that moment. The robot follows as you drag, so you can find the exact place you want. Then press Play and the show carries on from there — it does not jump back to the beginning. Pause and Play again also continues from where it stopped. ⏹ Back to start is the one button that returns to zero on purpose.

The bar used to be a small slider mixed in with the Timeline buttons, and it moved around whenever the buttons wrapped onto another line — so it could not be found. It now has a row of its own and stays put at every screen size.

A move's music can repeatnew

Press ♪ on a move, choose a track, and tick repeat. The track then plays again and again until the show ends or you press Stop, instead of falling silent when it reaches its end.

The repeat is saved inside the sequence file, so it works however you start the show: the ▶ Run on robot button, the module's own page, or the hub. The restart is quick but not a seamless join — there is a short gap while the file is reopened.

Clicking a move also moves the play clock therenew

Clicking a move used to show the pose but left the play clock wherever the last run stopped, so pressing Play carried on from a different point in the show than the one on screen.

Now the clock and the scrubber jump to where that move begins — everything before it, waits counted. Press Play and the show starts at that move, at that move's own speed. A suspended keyframe is stepped over the same way the show itself steps over it: the clock lands where the run jumps the gap.

The crash check now warns instead of blockingnew

The collision check runs while you pose the robot, while you play, and before Run or upload. What changed is what happens when it finds something.

The 3D preview always plays. Watching where the movement goes wrong is how you fix it, so nothing stops you seeing it. Whether it also reaches the robot is a separate question, and it is asked only when a module is actually connected: you get one confirm naming the bad keyframes, with OK = do it anyway and Cancel = stop and fix it. Refuse, and the preview plays on its own while the arm stays where it is.

Before this, Run and upload were blocked outright with no way past — and the check works from your rig's dimensions, so a rig that does not match the real robot could call a perfectly safe move a crash and leave you stuck. Forcing is allowed because it is your arm and you can see it.

Play was the dangerous one. It warned that only the 3D preview would play — and then drove the real arm anyway. It said one thing and did another, on the single path where being wrong bends metal. All three routes now go through one gate.

Permission lasts for one action. Editing the timeline withdraws it, so a “yes, run it anyway” given for one movement never quietly covers a different one.

RELAX now relaxes every jointfixed

Nine servos went limp on RELAX and SHRUG stayed stiff. The loop was never wrong — it always covered all ten. Detaching a servo only hands the pin back to plain GPIO; it says nothing about what level the line settles at. On a pin with an internal pull-up the line then sits high, and a servo watching a permanently high line holds its position instead of going limp.

SHRUG is on GPIO 15, a strapping pin the ESP32 pulls up at reset. The other nine happened to settle low, so they appeared to work. RELAX now drives every servo line low itself — saying “no pulses” rather than hoping — which is correct on every pin, not only the lucky ones.

QC previously covered RELAX only as a command that interrupts a sequence. It now also checks that it reaches every joint, that a relaxed line is really idle, and that no per-joint loop quietly stops at the eight arm joints and leaves WAIST and SHRUG behind.

Playback is much lighterfixed

Studio lagged while playing and froze when you came back to the page. The cause was work, not logic. The joint slider row was rewritten on every tick — six properties per joint, sixty writes a frame — and two of those were the travel limits, which had not changed. Setting a slider's min/max makes the browser re-check and clamp its value, so those were the expensive ones.

On top of that, the show clock is called from both the animation frame and a timer, so the picture was being redrawn about 76 times a second on a 60 Hz screen. Together that was roughly 4500 DOM writes a second for a row that mostly had not changed.

Now a value is written only when it actually differs, the limits only when the rig changes, and painting happens once per animation frame. Time still advances on whichever timer fires — that is what keeps a hidden tab moving — only the painting is limited.

Dragging the timeline moves the real armnew

Scrubbing used to move only the picture. Checking one move without playing the whole show is the reason the scrubber exists, and a preview that moves while the robot stays put is the one thing you cannot check against. The arm now follows the scrubber, using the same path a slider drag does — so it carries the link's own round-trip timing instead of easing at the module's speed setting.

Nong Studio no longer leaks graphics memoryfixed

Studio could take the whole machine down after a while — not with an error, just a crash. That is the signature of running the graphics card out of memory.

Rebuilding the 3D robot freed its geometry but never its materials, and a fresh material is created for every mesh on every build. The robot is rebuilt on every rig edit, so tuning the rig leaked a material — and its compiled shader — on every change. Removing an object from the scene only drops the JavaScript reference; the buffers stay on the card until they are handed back explicitly. Twenty-five rebuilds now leave the counters exactly where they started, and QC measures it rather than trusting it. Textures are deliberately left alone: they are cached and shared between builds.

The viewport size watcher was also made self-limiting, so it can never re-trigger itself and spin the processor.

Move your whole setup to another PCnew

Everything Nong Studio remembers — your tuned rig, your saved default, the STL assignments, the panel width — lives in that browser on that PC. Tuning a rig on the workshop machine and finding the show laptop knows nothing about it is what this fixes. In Studio's Setup tab, under “Move your setup to another PC”.

By file: Export writes one JSON file; copy it across and press Import. It is applied straight away and kept in that browser's cache.

Over the network: on the PC that has the setup press Share; on the other PC press Find PCs, pick it from the list, press Get. The search looks for other mice hubs on the same network, so no address has to be typed — though you can type one if the search cannot see it.

The transfer goes through your own hub rather than straight from the browser: a page served by one hub is not allowed to read another hub's response, so the hub does the fetching and hands it back. Sequences and projects are deliberately not included — those are already files on the hub. Neither is the zero-calibration login, which is per machine.

Shrug: a 4-bar linkage is not a see-sawnew

One servo drives the linkage that lifts both shoulders, so there is only ever one angle to command. But a 4-bar does not lift the two sides by the same amount, and the ratio changes across the travel. The preview rocked a single rigid bar, so it always drew the shoulders as exact mirror images — which is not what the robot does. The robot was right the whole time; the picture was wrong.

Measure it once, in the rig setup: set SHRUG to a few angles and note how far each shoulder actually rose, in millimetres, up positive. Two rows is the minimum; more rows describe the curve the linkage really follows. The preview then places each shoulder at its own height and stops rocking the bar, so the rotation is never counted twice on top of your measurement.

Measured beats computed here: the real linkage carries horn spline offset, bearing slop and mounting error, none of which the CAD model knows about. Leave the table empty and nothing changes — every rig saved before this keeps looking exactly as it did. Past the ends of your measurements the value holds rather than extrapolating a shoulder off into space.

Only one thing drives the servos at a timefixed

The module keeps a sequence and plays it on its own clock — that is what lets a show survive this page closing. But it meant the module could still be running when you came back, and pressing Play then had the browser streaming poses as well: two clocks on one robot, the arm fighting itself. Worse, Stop only stopped the browser, so the servos kept moving from the module's own sequence.

Play, Pause and scrubbing now all stop the module first. Taking control takes it completely.

A show keeps running when you leave the pagefixed

A hidden browser tab has its animation loop stopped and its timers slowed to roughly once a minute. No trick changes that reliably. The sequence ran at the wrong speed, or simply stopped and sat still until you looked at the page again.

So Studio stops trying to be the clock. When a show is playing and you switch away, the whole sequence is handed to the module, which plays it on its own 50 Hz timer — it keeps going with the browser minimised or closed completely, and it interpolates with the same formulas the preview uses, so the motion is identical rather than merely similar. Coming back, the page says the module is running it. Press Stop to end it.

Coming back also used to hang the page for a moment: the play head was advanced by the whole time you were away in a single step, so the pose jumped across the show and every joint was re-sent at once. One tick can no longer advance the show by more than a frame.

The USB lagfixed

The hub waited up to 80 ms before every command, to let a half-written log line finish. That cost is paid on each command and is worst exactly when the board is chatty — which became normal once every module started hosting a hotspot. On live pose streaming (about 30 commands a second) it was most of the delay, and the arm visibly trailed the sliders. The blank-line reply marker already tells a reply apart from a stray log line, so the wait was doing nothing and is gone.

The 3D view no longer covers the settingsfixed

One wide row in the side panel could push the panel wider than its 320 px, which silently shrank the 3D viewport — but nothing told the canvas to resize, so the render spilled over the settings and covered the controls. The panel is now a fixed track that wide content scrolls inside, and the canvas watches the viewport element itself, so it follows every size change: dragging the splitter, switching tabs, a scrollbar appearing.

One design system across every pagenew

The hub, this help page, the RGB page, Nong Studio and the module's own website read their colours, radii and spacing from one file: shared/web/mice.css. They used to hold six copies of it, each one commented “the shared design system” and none of them shared — they had already drifted into three different corner-radius scales and four names for the same grey caption.

Every page links it at /mice.css. The board serves that same URL itself: the stylesheet is compiled into the firmware, so a module looks the same whether you reach it over WiFi or through the hub over USB. QC fails if a page declares its own tokens, hardcodes a colour that is already a token, forgets the link, or if the copy in the board's flash is not byte for byte the shared file.

Dark stays the permanent default: the show area is kept dark and a bright screen spills light into the event.

Flashing says which board, and which PCnew

Overwriting firmware cannot be undone from this screen, it takes about a minute, and the board is usually in someone's hands across the room. The old question named a COM port or an IP address — neither tells you which of the boards in the room you are about to overwrite.

The confirm now names the board (its name, its id and the type it runs now), what it will become and whether that is a change, how it is reached (this PC's cable, or WiFi), and which PC is doing it, by name. That last one matters because several machines at a venue run this same hub on the same network, so being on the wrong browser tab is the easy mistake.

Cancel is the prominent button and the one under your thumb; overwriting is styled as destructive and has to be reached for. Escape cancels. QC clicks Cancel and then checks the hub, not the page — a confirm that closes while the write has already started would be worse than no confirm at all.

The hub asks for a password before it does anythingnew

The hub listens on every network connection so a phone on the same WiFi can reach it. Until now that also meant anyone on that WiFi could drive the servos or reflash a board. Now anything that changes something needs a login.

Looking stays free. The module list, the status of every board, this help page and the pages themselves all work with no password — someone checking whether a board is alive should never meet a password box.

Two details that are easy to get wrong. First, the rule is not “GET is safe”: /api/usb/cmd is a GET that moves the arm, so the gate is a list of what changes something, not a rule about the kind of request. Second, stopping is never gated — a password prompt while an arm is about to hit someone is a safety failure, so starting a show needs a login and ending one never does.

On first run the hub prints a generated password in its own window, on the PC. It is never shown on a page and never sent over the network, so seeing it means standing at the machine. It is stored hashed, five wrong tries locks that caller out for a minute, and a module on another PC needs a login on that PC too.

Tools work with nobody signed innew

At a venue you often need a tool in your hand before anyone has signed in. So the Tools and the module pages open with no login at all — Reconize, ESP32 camera, Voice, Studio and this help page included.

Everything else asks first. Where Flash firmware, Settings, the lights or a card that moves a robot would be, you see one line saying Sign in to use this, pointing at the page's one login box. Sign in and the cards come back in place, on the same screen — you are never sent to another page to find a password box.

This is not the lock. The lock is the list above, and it is on the hub: the robot does not move for anybody who has not signed in, whatever a page shows. The box decides what you see, so a card nobody marked is a card that still refuses when pressed.

Which pages open freely, and which cards ask first, is one file: config/page_access.json. The words on the box are in it too, so they can be changed without touching any code. If that file is ever broken, nothing is hidden and the hub says which file to fix — hiding the whole screen because the file describing it is broken would help nobody.

One line per log, one writenew

The board writes its log lines to the same port it answers commands on. A log was printed in two steps — the text, then the line ending — so a WiFi event, which runs separately, could land between them and stick its message onto the end of a reply. On the bench that looked like OK joining lift-test now (WIFI for progress)[wifi] disconnected, reason=8, and the PC read the whole thing as the answer.

Every log now goes through one helper that builds the line and hands it over in a single write, which cannot be split. The subsystem names — boot, sys, wifi, sd, seq, ota, cam — live in one list instead of being typed at 36 places, a long line is cut with a visible ... rather than lost, and a log can never contain a line break in the middle, which would have looked like a second reply.

Keyboard and motionnew

Every page now shows a visible focus ring when you tab through it — three of the four had none — and every page respects prefers-reduced-motion, so animations stop for anyone who has asked their system to stop them. Touch targets are at least 36 px wherever the pointer is coarse.

Everything works with the keyboard alonenew

Tab reaches every control on the hub, the module website and Nong Studio, and Enter presses it — useful with a broken trackpad, a laptop on a shelf, or a screen reader. The one place that was mouse-only was the Studio timeline: a keyframe could only be selected by clicking its chip. The move number is now a button (“go to move 3”), so the whole timeline can be walked with Tab.

QC opens each page in a real browser, walks every tab, and fails if anything is drawn as clickable but cannot be reached by Tab, or if a control looks the same focused as unfocused.

The hub says when its own program is out of datenew

MiceHub.exe is built from this source tree, and it goes out of date the moment the source changes. A hub running yesterday's build answers every request happily with the newest fixes missing — that really happened, and the only clue was a password that did not match.

The build now carries a receipt (a checksum for every source file that went into it), and the running hub compares it against the tree beside it. If they differ, a caution banner names the files that changed and the command that rebuilds it: python -m PyInstaller --clean MiceHub.spec. If MiceHub.exe is running, the build automatically closes it to avoid Windows file locks (or you can run taskkill /F /IM MiceHub.exe). On a PC that has only the program and no source — a venue laptop — there is nothing to compare, so it says nothing rather than guessing.

The hub tells the truth when it cannot reach anythingfixed

A failed scan used to replace the module list with the words "scan failed". Now the hub keeps the modules it last actually found, marks them plainly as old (“showing what was found 40s ago — these may no longer be there”), and offers a Try again button. The list also carries a quiet “checked just now” line, so you never have to wonder whether the page is frozen.

A control panel that goes blank when the network hiccups is broken however good it looks; one that keeps presenting old robots as if they were still there is worse. QC drives this for real — it loads the hub, breaks the scan endpoint, and fails if the list blanks, if the data is not marked stale, or if there is no way to retry.

Groups: which modules are allowed to linknew

A module belongs to a group — your installation. Its own hotspot password is derived from the group name, so every module in one group shares it automatically and nothing has to be typed twice.

That is what makes automatic linking safe. With no venue WiFi a grouped module scans, finds a neighbour's hotspot and joins it without ever having met it, because the only hotspot it can actually get into is a group-mate's. Two companies working the same site each let their own modules find each other, and neither can touch the other's. An ungrouped module never goes hunting: it would be using the shared built-in password, which proves nothing about who owns the board.

Set it in the hub's Network tab — tick the modules that belong together and name the group — or with GROUP <name> on any channel.

A module's own WiFi password, and changing itnew

Every module raises its own WiFi, named after the module. To get in the first time the password is 12345678 (a module in a group uses the group's password instead). Then open http://192.168.4.1/ and log in.

Choose your own with APPASS <password> (8 to 63 characters, no spaces); APPASS CLEAR goes back to the default. APPASS alone says which one is in use.

Modules in one group still find each other after an owner changes a password: the hub talks to every module, so every two minutes it reads each one's password and hands it to its group-mates (PEERPASS <wifi> <password>, PEERPASS CLEAR forgets them). A module in no group is never given any.

Talking from a phone: sound straight to the robotnew

Join the robot's own WiFi, open http://192.168.4.1/, log in, and in the speaker card tick song (pick a file on the phone), microphone, or both, then press Send sound to the robot. Each switch works while it plays, so the song keeps going while the microphone comes and goes. No hub and no PC are needed.

A phone browser only gives the microphone to a secure page, and the robot's page is not one. On Android Chrome open chrome://flags, find Insecure origins treated as secure, add http://192.168.4.1 and relaunch. A song file works without this.

Or, on any phone: tick microphone on the robot's page and press Microphone page. The robot opens its own secure page (TALK ON) at https://192.168.4.1/talk. The phone warns once about the certificate, because the robot made it itself; choose to continue. Type the robot's login there and press Send. The secure page costs the robot memory, so it closes after 10 quiet minutes (TALK OFF closes it at once).

A browser cannot hear other apps on the phone, so music playing in another app cannot be sent; pick the song file instead.

A cold start with no WiFi used to strand every modulefixed

A neighbour was only recognised by a name the module had already seen, and a module that just booted has seen nobody. So with the venue network down, every module sat on its own hotspot unable to find any of the others. Found by pulling a module's USB cable and running it from a charger. Grouped modules now recognise each other on a cold start.

A weak link moves to a stronger neighbournew

Falling back only when WiFi fails misses the case that actually hurts at a venue: a module far from the router still connects, just badly — commands arrive late and the show stutters. Signal strength is now checked too. If the show network is weak and a neighbouring module's hotspot is clearly stronger, the module joins the neighbour and is reached through it.

It comes back once the show network is properly good again, not merely less bad. The two thresholds are deliberately different: with a single one, a module sitting near the boundary flips between networks forever, dropping its link each time — which at a show looks exactly like the robot randomly freezing.

WIFI reports via="<module>" whenever a module is leaning on a neighbour, so it is never a mystery. The rule is a pure function unit-tested on a PC, because a real −80 dBm signal cannot be made to appear on a bench.

Which WiFi a module uses, and how to get backnew

Credentials set on the board (SET WIFI, stored on the chip) always win over the ones compiled into config/conf_network.h — those are only the factory default for a board nobody has set up yet. Both currently point at the same network.

WIFI CLEAR forgets what was set on the board and goes back to the built-in one, immediately. Without it a module could only ever be moved from one named network to another, so a board pointed at a bench hotspot had no way home short of a reflash.

One USB cable runs the whole installationnew

The usual situation at a venue: there is no usable WiFi. Plug the PC into any one module and let every other module join that module's own hotspot. The hub lists them under the cable and each one gets its normal buttons — its website, Nong Studio, file upload, sequences — even though your PC has no route to it at all.

Internally the hub addresses them as usb:COM11@nong: over this cable, then through it to the module named nong. It is a name, not an address, so it keeps working when the hotspot hands out a different one. Nothing else in any page changed — only the device string.

The same form works over WiFi (wifi:10.0.0.5@nong) when the module you can see is the one with the good signal.

Reach a module through another modulenew

A module parked out of router range joins a nearby module's hotspot — but it is then on that module's private network, where the PC has no route to it. So the module it joined forwards for it. PEERS lists what a module can see, and REACH <ip|name|id> <command> runs a command over there and hands back exactly what that module answered:

PC → USB → lift-test → its own hotspot → nong
REACH nong PING → PONG 67 nong nong

It is the same shape as the RS485 bridge (#3 GOTO 2) — one command in, one reply line out — so the hub's device routing and the module website's console needed no changes at all.

It is for finding and configuring a module, not for driving one during a show: it waits up to 800 ms for the far module, so it answers ERR busy rather than reach through while this module is mid-move and stop a joint dead. In a show, address the module directly or use RS485.

A reply is never a stray log linefixed

The module logs to the same serial line it answers on, and the two used to collide in three different ways. All three were found on the bench with two boards reconnecting, and all three are now covered by QC:

A half-eaten log line came back as the reply. The hub cleared the buffer before each command, which could cut a log line in two. The orphaned tail had no [tag] on it, so the log filter did not recognise it — SET WIFI answered "Hz-only network — ESP32 is 2.4GHz only)".

A log line was glued onto the end of a reply. Serial.println() is two writes — the text, then the newline — so a WiFi event on another task could land between them. The board now writes each reply as a single "\n" + reply + "\n", which no other task can get inside.

Every reply came back shifted by one. During a reconnect, 49 of 60 commands returned the previous command's answer. That leading blank line is now the marker the hub looks for: a real reply always has one in front of it, an orphaned tail never does. The same hammer test on real hardware now scores 50 of 50. A board running older firmware still works — without the marker the hub falls back to the old behaviour.

RS485 bus — many modules on two wires

Address any module with #<id> <command> and it answers @<id> …. #* PING takes a census of the whole bus. Modules bridge # lines onto the bus, so one module's USB port reaches every other module behind it.

Accounts stored on the board

The website's Setup gate is backed by real accounts in NVS (default super_admin / admin123 and admin / admin123, added on start-up to any board that lacks them; existing accounts are kept). A default password shows a please change note but does not lock Setup. AUTH, plus USER LIST|ADD|DEL|PASS — user operations require valid credentials. The raw command channel stays open for scripts and RS485.

Speaker

Nong module — humanoid upper body

Two arms and a body: 10 logical joints driven by 10 servos, from one ESP32. Every angle is a joint degree — the physical joint — so poses stay valid no matter what servo or gear is fitted.

Motion

Whole-body and single-joint moves

POSE takes all 10 angles, - keeps a joint where it is, and an old 8-value pose still loads. JOINT WAIST 60 moves one joint by name.

Smooth interpolation with an honest time floor

Every move eases in and out over a duration T. A T shorter than the servos can physically achieve is raised, per joint, so the interpolation never "finishes" before the real arm arrives. The editor enforces the identical formula while authoring.

Hold, freeze and go limp

STOP freezes mid-move at the pose reached, and silences the speaker — stopping a show means quiet as well as still. RELAX unpowers the servos so you can pose the arms by hand; ATTACH powers them again holding the current pose. HOME returns to the neutral pose.

Calibration — all per joint, all live, all persistent

Set zero by hand

SETZERO declares wherever the arms are now to be home. Trim absorbs the offset, so the arm does not move when you run it. It leaves your chosen start angles alone.

Servo offset — nudge one joint that sits a few degrees out

A servo horn only fits back on in whole teeth — about 14° of shaft — so a joint often lands a few degrees off even when everything else is right. In Nong Studio's Setup tab, the Servo offset card gives every joint a −, a number and a +. Press until the arm looks straight; each press is half a degree, and the arm moves as you press. 0 clears one joint, Clear all clears the lot.

The number is degrees on the arm, so the same value shifts every joint by the same visible amount whatever its gearing. The robot keeps it in its own memory, and your saved poses and sequences all keep working — an offset only changes where that one joint sits, not what any pose means. Range is −30 to 30: past that a joint is assembled wrong, and a bigger offset would only drive the servo into its own end stop.

The command is OFFSET — OFFSET L_EL_P 3 for one joint, OFFSET ALL 0 to clear every one. OFFSET? reports them. Set zero on the Robot tab is the all-at-once version: it takes the pose the robot is standing in and calls that home.

Where each joint starts — your own angle, not always 90°

Every joint has its own start angle: where it goes when the robot is switched on, and where HOME and the Neutral pose button send it. Set it in Nong Studio's Setup tab, in the start° box beside each joint, then press Send rig to robot. Or shape the robot by hand and press Keep this as neutral, which sends all ten at once.

The command is NEUTRAL — one joint (NEUTRAL WAIST 60), all of them (NEUTRAL ALL 90), or the whole pose in one line. NEUTRAL? reads back what the robot is set to. Setting it does not move the arm; press Home when you want it to go there. The robot keeps these in its own memory, so they survive being unplugged.

Per-joint servo, gear, pulse, travel and frame rate

GEAR (pinion:gear), PULSE (µs range + max °/s), RANGE (servo travel 180/270°), RATE (frame rate Hz), LIMIT (joint travel). Nothing is hard-coded for the whole arm — a 270° shoulder next to a 180° elbow is fine.

Presets via SERVO <joint|ALL> <type>: mg90s, pdi1181mg, tiankong35, generic180, generic270.

servo travel ≠ joint limits. servo_range is how far the servo turns — a property of the part you bought. joint_min/joint_max is how far the joint may turn — a property of your mechanism. Poses are always joint degrees, so fitting a 270° servo is a one-number change and every saved sequence keeps working.

Calibration survives a power cycle — with or without an SD cardfixed

Every change is saved twice: to the chip's own memory always, and to /data/nong_cal.yaml as a readable copy when a card is fitted. So a board with no card keeps its gear, limits, pulses, travel, rate and zero instead of coming back on the factory defaults every time you unplug it.

At boot the card file is applied first and the chip copy second, so the chip copy wins — it is written by every calibration command whether or not a card is present. CAL reports which copies exist; CAL CLEAR forgets both and a reboot returns to the defaults.

Playing this PC's sound on the robot. Open the module from the hub, find the Speaker card and press Play this PC's sound. Why it asks to share a screen. Windows only lets a browser take the PC's sound together with a screen or a tab — there is no sound-only choice, in any browser. Does sharing a screen make it slower? No. The picture is never sent and never encoded — the video is stopped before the sound is wired up at all, so the robot hears exactly what it would hear from a sound-only share. FWBEGIN | FWDATA | FWEND | FWABORT | FWSTATNew firmware over any channel, including RS485. The other two ways both need something a bus does not have: esptool reaches the ESP32's boot loader by pulling EN and IO0 with the cable's DTR and RTS lines, and POST /api/ota talks to the board's own web server. A two-wire bus has neither, so instead the board writes its own spare slot from ordinary commands and the link underneath stops mattering. Each chunk carries its number and its length — a line cut short is still valid base64, so without the length a short chunk decodes silently and the image ends up wrong. Out-of-order and short chunks are both refused without advancing, so the sender just repeats one. The image is checked against its md5 at FWEND, while the board is still running firmware that works, and only a good one causes the reboot; FWABORT leaves it on what it had. It is slow — minutes, not seconds — which is the price of having no reset line. Started for you by the hub's Firmware tab
PERF?Is the board keeping up? How long its main loop takes, the widest gap between two servo updates while moving (20 ms is on time), what held it up longest, free memory, and how many times it has restarted since it was switched on, with the reason for the last one. CRASH, WATCHDOG or BROWNOUT there means something is wrong. Each ask starts a fresh count. python tools/bench_perf.py <port or address> runs every task on a real board and reads this around each one
